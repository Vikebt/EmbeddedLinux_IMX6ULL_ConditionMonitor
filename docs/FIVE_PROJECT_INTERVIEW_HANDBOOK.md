## 1. 面试回答的固定骨架

不要从定义背到定义。统一使用下面五句话：

1. **一句定义**：它解决什么问题。
2. **项目场景**：我在哪个项目遇到这个问题。
3. **代码证据**：具体到模块、函数或数据流。
4. **工程取舍**：为什么选它，没有选什么，代价是什么。
5. **验证边界**：什么已经由测试证明，什么必须上板后才能证明。

例如，回答“volatile 和 atomic 有什么区别”：

> `volatile` 约束编译器对一次对象访问的优化，常用于硬件寄存器或会被中断改变的标志，但它不提供线程间原子性和同步顺序。多源光电项目的停止标志使用 `std::atomic`，复合传感器结果则用 mutex 保护后复制快照；STM32 外设寄存器由 CMSIS 的 volatile 定义访问。这样我不会把“每次都读内存”误说成“线程安全”。宿主测试和代码审查能证明同步结构，硬件寄存器时序仍需上板验证。

## 3. C/C++ 高频题与项目回答

### 3.1 `static`、`extern`、`const`、`volatile`

- `static` 在文件作用域控制内部链接，在函数内延长对象生命周期，在类中表示成员属于类型而非实例。
- `extern` 声明符号定义在其他翻译单元；C++ 调 C 接口时用 `extern "C"` 关闭 C++ 名字改编。
- `const` 表达不可通过该接口修改，利于建立只读契约，但不等于对象存储绝对不可变。
- `volatile` 不等于线程安全。它不提供原子读改写、互斥或 happens-before。

项目落点：STM32 的硬件寄存器访问依赖 CMSIS 的 volatile 类型；跨任务传数据使用 FreeRTOS queue/mutex。Linux 项目的线程停止标志用 atomic，复杂结构用 mutex 快照。面试时要主动指出二者不能互换。

### 3.2 栈、堆、内存泄漏与 RAII

栈对象随作用域自动销毁，堆对象必须明确所有权。真正的问题不是“堆一定慢”，而是生命周期、碎片、异常路径和释放责任。

- LiDAR 的 socket/epoll fd 在构造失败分支和析构中成对释放。
- 光电融合取消 detached 线程，析构前先通知、再 join、最后释放设备。
- 驱动项目的 `UniqueFd` 和 `BufferGuard` 让异常/正常退出共用一条释放路径。
- 内核驱动用 devm 管理与 device 生命周期绑定的资源。

回答 RAII 时可以说：资源不限于内存，还包括 fd、线程、设备状态、锁和内核注册关系。

### 3.3 指针、引用和智能指针

- 指针可为空、可改指向，适合表达可选对象或底层地址；引用通常表达必需别名。
- `unique_ptr` 表达唯一所有权且可移动；`shared_ptr` 表达共享所有权，但有计数开销和环风险；`weak_ptr` 用于观察共享对象而不延长生命周期。
- 不要为了“用了 C++11”而滥用 `shared_ptr`。能由栈、父对象或 `unique_ptr` 表达的所有权更清楚。

项目落点：驱动用户态对 `DIR*` 使用 `unique_ptr<DIR, Deleter>`；fd 使用自定义可移动、不可复制 RAII 类型。它比口头解释更能证明理解“所有权”。

### 3.4 左值、右值、移动语义

移动不是“把内存搬走”，而是转移资源所有权，使源对象保持可析构、可赋值但值通常未指定。只有资源型对象的移动才有明显收益。

项目落点：`UniqueFd` 禁止复制、允许移动；移动后源 fd 置为 `-1`，防止二次关闭。面试可顺带解释 Rule of Five：一旦类自定义析构且拥有资源，应审视复制/移动构造和赋值。

### 3.5 内存对齐、大小端和严格别名

- 网络与传感器数据是字节流，解析前必须检查长度，再处理端序。
- 不要用不兼容指针强转读取 float，这可能违反对齐和严格别名规则；用 `memcpy` 更稳妥。
- IIO scan 中时间戳需要 8 字节对齐，结构体 padding 必须先清零，避免泄露未初始化内核内存。

项目落点：LiDAR PCAP 路径先检查截断帧；光电融合的浮点解析改为 `memcpy`；IIO 驱动每次 push 前清零完整 scan buffer。

## 4. FreeRTOS 与并发高频题

### 4.1 任务、线程和进程

FreeRTOS task 与 Linux thread 都是调度实体，但隔离模型不同：FreeRTOS 任务通常共享一个 MCU 地址空间；Linux 进程有独立虚拟地址空间，同一进程内线程共享代码、堆和 fd。

项目回答：小车中任务通过队列交换命令，避免共同写电机；光电融合在同一进程的 ROS/Qt 工作线程之间用 mutex/atomic；驱动项目把可失败策略放用户进程，内核只提供机制。

### 4.2 queue、semaphore、mutex、critical section 怎么选

- queue：同时传递数据和同步，最适合明确所有权交接。
- binary/counting semaphore：表达事件或资源数量，不负责数据本体。
- mutex：保护共享资源，通常带所有者语义和优先级继承。
- critical section：屏蔽调度/中断的短小原子片段，不能包围耗时 I/O。

项目落点：体温仪 I2C 用 mutex；显示任务只在复制共享标量时进临界区，RTC 访问放在外面；传感器数据通过队列流动。

### 4.3 为什么 ISR 要短

ISR 占用期间会增加系统中断延迟，且可调用 API 受上下文限制。正确做法是快速读取/确认硬件状态、形成最小事件，用 `...FromISR` 唤醒任务，把业务和阻塞操作留在任务上下文。

项目落点：小车 USART ISR 只收两个字节、组帧并覆盖长度为 1 的最新值队列；病房判断、转向和电机输出在任务中完成。

### 4.4 优先级反转和死锁

优先级反转发生在高优先级任务等待低优先级任务持有的资源，而中优先级任务又长期抢占低优先级任务。mutex 的优先级继承可缓解有界反转，但不能替代短临界区和良好资源设计。

死锁经典条件是互斥、占有且等待、不可剥夺、循环等待。项目中的规避方式包括：单一电机写入者、尽量不嵌套锁、I/O 不放在锁内、停止时先关闭队列唤醒等待者再 join。

### 4.5 队列满与反压

没有一种满队列策略适合所有业务：

- 控制/实时感知重视新鲜度：丢最旧，保最新。
- 必须完整处理的离线任务：阻塞或持久化，但要接受延迟增长。
- 关键命令：应显式失败、重试或提升容量，不能静默丢弃。

体温仪、小车与 LiDAR 都使用“最新值/DropOldest”语义；光电点云保存队列最多 3 帧，慢磁盘时丢旧，避免内存无界增长。回答时必须同时说出 dropped 指标，否则丢包会变成不可观测故障。

### 4.6 非阻塞状态机和 Tick 回绕

长时间 `delay` 会让任务无法响应新事件。小车把转向、提示和掉头拆成状态，以进入时间推进。时间判断使用无符号差值 `now - start >= duration`，只要比较区间小于计数器半周期，就能自然跨越回绕。

## 5. Linux 进程、线程与 I/O 高频题

### 5.1 线程同步为什么不能只靠普通 bool

C++ 中一个线程写、另一个线程无同步读普通对象会产生 data race，行为未定义。`volatile bool` 也不能修复。

光电融合使用 atomic 管理单值控制标志；含 string 或多个关联字段的结果在同一 mutex 下复制完整快照。原则是：atomic 保证单对象并发语义，mutex 保证一组不变量。

### 5.2 `detach` 和 `join`

`detach` 不是异步的通用答案，它切断了生命周期控制；对象析构后 detached 线程仍可能访问成员。光电融合重构后统一采用 stop flag + join/wait，再释放设备。只有能证明线程完全不引用外部短生命周期对象时，才考虑 detach。

### 5.3 `select`、`poll`、`epoll`

- `select` 有 fd 集合拷贝和常见的 fd 数量限制，每次返回后集合还要重建。
- `poll` 用数组描述 fd，无固定 `FD_SETSIZE`，但每轮仍线性扫描。
- `epoll` 把关注集合保留在内核，等待返回就绪事件，适合大量或多类型长期 fd。

项目取舍：LiDAR 当前只有一个 UDP socket，`poll` 也够用；保留 epoll 是为了统一未来多 socket。驱动项目则真实地把 IIO fd、timerfd 和 signalfd 放进同一事件循环，避免忙轮询和“一事件一线程”。不要回答“epoll 永远更快”，fd 少时复杂度收益有限。

### 5.4 LT、ET 与非阻塞读

LT 只要仍可读就会继续通知，较易写对；ET 只在状态变化时通知，必须非阻塞并循环读到 `EAGAIN`。驱动用户态即使采用 LT，也按非阻塞方式 drain，并保留不足一帧的尾部字节，下次事件继续拼接。这说明“read 一次等于一帧”是错误假设。

### 5.5 signal 与 `signalfd`

普通 signal handler 能安全调用的函数极少，修改复杂对象容易出错。`conditiond` 先阻塞 SIGINT/SIGTERM，再用 signalfd 把信号变成 fd 事件，与 IIO、timerfd 共用普通控制流，退出时让 RAII 正常工作。

### 5.6 条件变量为何需要谓词

条件变量允许虚假唤醒，且通知可能发生在等待前。LiDAR 的 `BoundedQueue::push/pop` 在循环谓词中同时检查容量/数据与 shutdown；关闭时 `notify_all`，防止线程永久等待。

## 6. 网络高频题

### 6.1 TCP 与 UDP 怎么选

TCP 提供面向字节流的可靠、有序传输和拥塞控制；UDP 保留报文边界、开销低，但应用要自行面对丢包、乱序和重复。

LiDAR 使用 UDP，是因为传感器持续高速发布，旧包重传的价值通常小于新包时效；这并不等于“UDP 更快所以不用管错误”。代码仍要检查来源、长度、系统调用错误和丢弃指标。RTSP 控制/媒体链路由既有协议栈处理，项目重点是断流后的有界指数退避。

### 6.2 TCP 粘包为什么出现

TCP 是字节流，没有消息边界。应用协议必须采用固定长度、分隔符或长度字段，并处理半包/多包。UDP 一次接收对应一个数据报，但仍可能因缓冲区不足被截断。

可关联回答：IIO 字符设备同样是字节读取接口，`conditiond` 用 pending 缓冲解决半个 scan 与一次多个 scan，展示了通用的流式解析思路。

### 6.3 重连为什么要指数退避

立即死循环重连会造成 CPU、日志和网络风暴。光电融合从 250 ms 开始翻倍，最大 5 s，成功后复位；等待拆成 50 ms 小步以快速响应停止。宿主测试覆盖完整序列。

## 7. Linux 驱动高频题

### 7.1 从设备树到 `probe` 的完整路径

1. DTS 在 ECSPI3 控制器下声明 ICM20608 子节点、片选、频率和 `compatible`。
2. SPI core 根据设备树创建 `spi_device`。
3. `spi_driver` 的 `of_match_table` 匹配 compatible。
4. core 调用 `icm20608_probe`。
5. probe 分配 IIO 设备、建立 regmap、读取 WHO_AM_I、初始化芯片并注册 IIO device。
6. 任一步失败立即返回错误，devm 资源随 device 生命周期回收。

面试时不能说“设备树加载驱动”；更准确是它描述硬件并参与设备与驱动匹配。

### 7.2 为什么用 IIO 而不是私有字符设备

IMU 是典型工业 I/O 传感器。IIO 已定义 channel、raw/scale/offset、sampling_frequency、trigger 和 buffer ABI。复用标准框架可直接获得 sysfs 与统一用户态接口，减少自定义 ioctl 和 ABI 维护。字符设备并非错误，但需要项目确有特殊数据/控制语义。

### 7.3 regmap 的价值

regmap 集中描述寄存器宽度、值宽度和 SPI 读标志，统一单寄存器/批量访问与错误处理。它不是“为了少写几行”，而是隔离总线细节，后续还可利用缓存和调试能力。

### 7.4 hrtimer 里为什么不能读 SPI

hrtimer callback 运行在原子上下文，不能执行可能睡眠的 SPI 传输。项目回调只调用 `iio_trigger_poll()` 发出采样事件，真正的 `regmap_bulk_read()` 在线程化 poll handler 中执行。这是中断“上半部快、下半部慢”思想在无硬件 DRDY 引脚时的等价落地。

### 7.5 sysfs 与 `/dev` 的区别

sysfs 是内核对象及属性的文本视图，适合配置和低频状态；`/dev/iio:deviceX` buffer 适合连续二进制样本。用户态按 `name` 枚举设备而不是写死 `device0`，因为 probe 顺序不稳定。

### 7.6 用户态与内核态怎样划分

内核只做设备机制：发现、寄存器访问、采样、时间戳和标准 ABI；倾斜/冲击阈值与故障状态机在用户态。理由是策略变化频繁、用户态更易测试，算法故障也不应扩大为内核故障。

### 7.7 为什么 scan padding 要清零

七个 16 位通道共 14 字节，后接 8 字节对齐的时间戳，结构中间会有 padding。若直接把未初始化结构 push 到用户态，可能泄露内核栈数据。驱动在填充前 `memset` 整个 scan。

### 7.8 驱动验证为何分 Host、Source、HIL

- Host：证明纯算法、回放、sysfs 假环境和 epoll 控制流。
- Source：用目标 ARM 工具链和 vendor 4.1.15 内核头编译，证明语法/API/架构兼容。
- HIL：证明真实 SPI、DT、时序、噪声、长稳和卸载路径。

本项目完成 Host、ARM 用户态交叉编译与隔离 vendor 4.1.15 内核模块联编；原始 vendor defconfig 缺少 IIO buffer/trigger 依赖，已在隔离内核副本中通过 Kconfig 集成补齐。尚未完成 HIL，不能把 `.ko` 可编译写成“模块已上板”。

## 8. 30 个高频追问速答

1. **为什么 `volatile` 不能做线程同步？** 没有原子性和内存顺序；用 atomic、mutex 或 RTOS 原语。
2. **mutex 与 semaphore 最大区别？** mutex 表达所有权并可做优先级继承；semaphore 表达事件/计数。
3. **临界区能包住 I2C/RTC 吗？** 不应，I/O 可能长时间阻塞；只保护短共享数据复制。
4. **ISR 能调用普通队列 API 吗？** 不能，应使用 `...FromISR` 并根据需要请求上下文切换。
5. **队列长度 1 有什么意义？** 表达 mailbox/latest-value，只关心最新观测。
6. **如何处理 FreeRTOS 栈溢出？** 启用 level-2 检查、hook、创建断言，并做高水位监测。
7. **CRC 能防掉电写一半吗？** 能检测损坏但不能保证原子提交；更严谨还要双槽/序号/最后提交标志。
8. **为什么状态机比 `delay` 好？** 不占住执行流，可继续响应新事件和故障。
9. **Tick 回绕怎么处理？** 用同宽无符号减法计算 elapsed，不直接比较绝对大小。
10. **普通 bool 停线程有什么问题？** 跨线程 data race；使用 atomic 或锁。
11. **atomic 能保护结构体一致性吗？** 通常不能；多字段不变量用 mutex 快照。
12. **为什么不 detach？** 无法可靠等待结束，容易对象析构后继续访问。
13. **条件变量为什么用 while/谓词？** 应对虚假唤醒、竞争和 shutdown。
14. **有界队列的价值？** 限制内存和最坏等待，把过载策略显式化。
15. **DropOldest 的代价？** 丢失完整性；必须统计 dropped 并确认业务重视新鲜度。
16. **epoll 一定比 poll 快吗？** 不一定；fd 少时差别小，epoll 在大集合/长期关注集更有优势。
17. **ET 为什么必须读到 EAGAIN？** 后续没有新边沿时可能不再通知，未读数据会滞留。
18. **read 为什么会半包？** 字节接口只保证返回可用字节数，不保证应用帧边界。
19. **fd 怎样避免泄漏？** 明确唯一所有权，所有失败路径释放，最好用 RAII。
20. **UDP 丢包怎么办？** 序号/时间戳、缓冲策略、丢包指标；实时流通常不重传旧帧。
21. **PCAP 回放为何不能 `abort`？** EOF 是正常生命周期事件，应返回状态并由上层收尾。
22. **重连为什么设上限？** 避免恢复过慢，同时防止请求风暴。
23. **设备树做什么？** 描述板级硬件连接与属性，供内核枚举和匹配，不承载业务逻辑。
24. **probe 里最先验证什么？** 总线通信与芯片身份；WHO_AM_I 错误就失败。
25. **devm 的价值？** 资源绑定 device 生命周期，简化 probe 失败和 remove 路径。
26. **IIO 比 ioctl 好在哪？** 标准传感器 ABI、channel/scale/buffer/trigger 可复用。
27. **为何 bulk read？** 一次事务获得同一采样窗口的数据，并降低总线开销。
28. **hrtimer 是硬中断吗？** 回调处在不可睡眠的原子上下文，工程约束与硬中断快路径相似。
29. **signalfd 的价值？** 把信号并入 fd 事件循环，避免复杂 async signal handler。
30. **C++14 是不是落后？** 目标工具链约束下选择可部署标准；关键是能说明缺失能力与替代实现。

## 9. 五个项目的 30 秒介绍

### 9.1 手持体温检测仪

> 这是 STM32F103 + FreeRTOS 的多源体温检测仪。我重构的重点不是增加页面，而是修正任务启动、数据新鲜度和配置可靠性：传感器通过有界队列传递最新数据，I2C 用 mutex 串行化，短临界区只复制共享快照；只有新鲜温度与有效 RFID 同时满足才生成记录。Flash 记录加入 magic/version/完整 CRC，默认配置不再包含凭据。主机测试证明融合策略和 CRC，外设时序保留为上板项。

### 9.2 智能送药小车

> 这是 STM32F103 + FreeRTOS 的视觉循迹送药车。我把 USART 中断缩到两字节组帧和队列通知，控制任务成为电机唯一写者，再用无阻塞状态机推进转向、提示和掉头。HX711 等待增加超时，Tick 计算覆盖回绕。主机测试证明状态转移和命令输出，但 PID、阈值和机械时长必须实车标定。

### 9.3 三维 LiDAR 感知

> 这是 ROS1/PCL 的 LiDAR 数据接入与点云处理流水线。我重构了 UDP/epoll 生命周期、PCAP 边界检查和并发流水线：所有 fd 错误路径可回收，处理级之间用可选择 DropOldest/Block 的有界队列，条件变量把 shutdown 放进谓词，线程按下游到上游停止并 join。主机测试覆盖过载和关闭语义；没有设备时不宣称吞吐与丢包率。

### 9.4 多源光电数据融合

> 这是 ROS、Qt、RTSP、串口与点云融合应用。核心问题是跨线程生命周期和快照一致性：我移除了 detached spinner 和混合回调调度，单值标志用 atomic，复合传感器结果用 mutex 复制完整快照；RTSP 使用有上限的指数退避，点云落盘使用 3 帧有界队列。宿主测试覆盖退避，完整 ROS/Qt/PCL 集成仍需目标环境。

### 9.5 I.MX6ULL 状态监测器

> 这是基于正点原子 I.MX6ULL 学习经历构建的可解释 Linux 驱动项目。ICM20608 通过 SPI/regmap 接入 IIO，hrtimer 只触发采样，可能睡眠的 SPI 读取在线程化 handler 完成；用户态按 sysfs 名称发现设备，用 epoll 统一 IIO、timerfd 和 signalfd，再由可主机测试的状态机判断倾斜、冲击和失联。Linux 宿主 5/5 测试、ARM 用户态交叉编译和隔离 vendor 4.1.15 内核 `.ko` 联编已通过，目标板加载与实板采样明确留作 HIL。
