# 04｜Linux I/O、事件循环与网络

本章对应原题 115～159、181～189。主线是：**文件描述符统一事件源，非阻塞 I/O 允许一个线程管理多个源，协议解析必须接受短读、丢包和重连。**

## 1. 网络分层与项目边界

### B01｜原题 115～119：OSI/TCP-IP 分层

面试不需要机械背七层，而要能把项目数据放进层次：

```text
应用层：LiDAR 私有报文、RTSP、ROS topic、conditiond JSON 输出
传输层：UDP（LiDAR）、TCP（RTSP 控制及常见流媒体承载）
网络层：IPv4
数据链路层：以太网
物理层：网线/PHY
```

分层的价值是把“报文含义、可靠性、寻址、帧传输”分给不同协议。项目没有自己实现 TCP/IP 栈，因此这些题为 `RELATED`，但能用实际数据路径解释。

### C01｜原题 120～131：HTTP、HTTPS、Cookie、DNS 与浏览器流程

这些题属于通用网络基础，不应强行绑定当前五项目：

- HTTP 是应用层请求/响应协议；1.1 的持久连接、2 的多路复用与头部压缩要区分。
- HTTPS 是 HTTP 运行在 TLS 上，通常用非对称密码完成身份认证/密钥协商，用对称密码传输数据；证书把公钥和身份由 CA 签名绑定。
- Cookie 是浏览器保存并随请求发送的数据，Session 通常是服务端状态，Token 是调用者携带的凭据表示；三者不是同一层面的互斥选项。
- DNS 把名称解析为地址，浏览器访问还涉及缓存、连接、TLS、HTTP、资源解析与渲染。

如果面试官问到，只按基础回答；除非项目真实增加 HTTP/TLS 上报，否则不要说“ESP8266 上传”就等于自己实现了 HTTPS。

## 2. TCP、UDP 与实时传感器数据

### A01｜原题 132、133、134：TCP 头部、握手与挥手

- **一句话结论**：TCP 用序号、确认、窗口、重传和状态机提供可靠有序字节流；三次握手同步双方初始序号和能力，关闭方向独立所以常见四次挥手。
- **从零解释**：TCP 不保留应用消息边界，发送两次可能一次读出，发送一次也可能多次读完。
- **底层机制**：SYN 消耗一个序号；ACK 确认已收到的下一个序号；FIN 只关闭一个发送方向。
- **项目场景**：P4 的 RTSP 连接由库管理 TCP/媒体协议，项目重构关注断流后的恢复，而不是自行实现握手。
- **代码证据**：P4 `rtsp_capture.cpp`。证据：`RELATED`，重连策略为 `CODE/HOST`。
- **工程取舍**：使用成熟协议库；应用仍需处理连接成功后断流、超时和重新初始化资源。
- **常见误区**：说“三次握手保证数据不丢”；可靠性还依赖序号、ACK、重传和流量/拥塞控制。
- **30 秒回答**：TCP 三次握手确认双向收发和初始序号，关闭两个方向所以常见四次。我的 RTSP 项目不重写 TCP，而是处理连接断开后的有界退避和线程退出。
- **2 分钟展开**：画 SYN、SYN-ACK、ACK 和 FIN/ACK 状态，说明应用边界不存在。

### B02｜原题 135～137：TIME_WAIT、2MSL 与断网

主动关闭方进入 TIME_WAIT，使迟到的旧报文在网络中消失，并能重发最后 ACK。2MSL 来自报文最大生存时间的往返考虑。拔网线不会立即神奇删除内核连接状态，应用何时发现取决于后续发送、超时、keepalive 和协议心跳。

P4 的 RTSP 不能只等待 TCP 立即报错，而要把“持续读不到有效帧”也纳入失败判断；当前项目验证的是退避序列，不声称覆盖所有 TCP 状态。

### A02｜原题 138、139：TCP 与 UDP 如何选择

- **一句话结论**：TCP 提供可靠有序字节流和拥塞控制；UDP 提供无连接数据报，保留消息边界但不保证到达、顺序或唯一性。
- **从零解释**：实时传感器可能宁愿丢旧包也不愿重传导致延迟；配置/控制命令通常更看重可靠性。
- **底层机制**：UDP 每个 datagram 独立，接收缓冲不足可能截断/丢弃；TCP 把数据视为连续字节序列。
- **项目场景**：P3 LiDAR 使用 UDP 连续接收点云包，P4 RTSP 由协议库管理，P1 ESP8266 上报接口不夸大具体可靠协议。
- **代码证据**：P3 `src/input.cc::InputSocket`。证据：`CODE`；真实网络性能为 `TODO-HIL`。
- **工程取舍**：UDP 需要长度、来源、序号/时间戳和丢包指标；TCP 需要处理半包、积压与重连。
- **常见误区**：说 UDP “一定更快”；网络拥塞时不受控发送可能更差。
- **30 秒回答**：LiDAR 持续高速采样更重视新鲜度，所以使用 UDP；代码仍检查来源、长度和错误，并在后续队列统计丢弃。可靠控制链才更适合 TCP。
- **2 分钟展开**：比较可靠性、边界、连接状态、拥塞控制、广播/组播和应用补偿。

### A03｜原题 181：网络字节序与安全解析

- **一句话结论**：网络字节序是大端；解析字节流必须先检查长度，再用转换函数或逐字节/memcpy 读取，不能直接解引用未对齐强转指针。
- **从零解释**：不同 CPU 端序可能不同，协议约定统一顺序才能互通。
- **底层机制**：`ntohs/ntohl` 转换整数；浮点和私有格式需要协议明确。未对齐和严格别名错误会产生 UB。
- **项目场景**：P3 PCAP/UDP 路径检查帧长；P4 浮点解析改用 memcpy；P5 IIO scan 使用明确通道布局。
- **代码证据**：P3 `InputPCAP::getPacket`，P4 串口解析，P5 scan 解码。证据：`CODE`。
- **工程取舍**：性能敏感时用 bulk read 后逐字段解析；正确性检查不能省。
- **常见误区**：所有主机都是小端所以直接 cast；把结构体通过 socket 发送就认为跨平台。
- **30 秒回答**：我先验证报文长度，再按协议端序解析；浮点采用 memcpy 避免未对齐和严格别名问题，不直接把字节指针强转为结构体。
- **2 分钟展开**：给出 0x1234 在大/小端内存中的顺序，并说明 IIO 是本机 ABI，不等于网络协议。

## 3. Socket 生命周期

### A04｜原题 182：客户端/服务端 socket 基本流程

- **一句话结论**：服务端通常 socket→bind→listen→accept→read/write→close；客户端 socket→connect→read/write→close；UDP 不需要 listen/accept。
- **从零解释**：监听 socket 接收连接请求，accept 返回新的已连接 fd；二者生命周期不同。
- **底层机制**：阻塞、非阻塞、超时和错误由 fd flags 与系统调用语义决定。
- **项目场景**：P3 是 UDP 接收端，socket→bind→设置非阻塞→注册 epoll；构造任何一步失败都清理已有 fd。
- **代码证据**：P3 `src/lslidar_ls_driver/src/input.cc::InputSocket`。证据：`CODE`。
- **工程取舍**：单 socket 用 poll 也够；项目保留 epoll 以统一未来多个传感器 fd，但不声称单 fd 性能更高。
- **常见误区**：忘记 bind 的地址/端口字节序；构造失败泄漏 socket；EINTR 直接当致命错误。
- **30 秒回答**：LiDAR 是 UDP 服务端式接收，不需要 listen/accept。创建、bind、nonblock 和 epoll 注册逐步进行，每个失败分支关闭已取得资源。
- **2 分钟展开**：描述 recvfrom 的来源地址、过滤策略和 graceful stop。

### B03｜原题 183：并发服务器用进程还是线程

多进程隔离强、故障影响小、通信成本高；多线程共享数据方便但需要同步；事件循环适合大量 I/O 等待。当前项目不是通用并发服务器，但 P5 的“一个 epoll 线程管理三个 fd”可作为第三种结构对比，不能把它说成高并发服务器压测结果。

## 4. I/O 多路复用

### A05｜原题 184：什么是 I/O 多路复用

- **一句话结论**：一个线程阻塞等待多个 fd 的就绪事件，避免为每个 I/O 源创建线程或忙轮询。
- **从零解释**：就绪只表示某次操作“现在不会按原方式阻塞”，不保证能读到完整应用消息。
- **底层机制**：内核维护等待关系，事件发生时唤醒等待者并返回就绪集合。
- **项目场景**：P5 同时等待 IIO、timerfd、signalfd；P3 等待 UDP socket。
- **代码证据**：P5 `apps/conditiond.cpp`，P3 `input.cc`。证据：`CODE`、`HOST`。
- **工程取舍**：事件循环减少线程协调，但长 CPU 任务不能堵塞 loop，需拆分或投递工作池。
- **常见误区**：把异步 I/O、非阻塞 I/O 和多路复用当同义词。
- **30 秒回答**：conditiond 用 epoll 把传感器、周期超时和退出信号统一成 fd 事件，一个线程阻塞等待，不需要忙轮询或三条线程。
- **2 分钟展开**：解释 readiness、短读、EAGAIN 和事件处理公平性。

### A06｜原题 185、188：select、poll、epoll 对比

- **一句话结论**：select/poll 每轮传递并扫描关注集合；epoll 把兴趣集合保留在内核并返回就绪事件，适合较大、长期的 fd 集合，但不是任何场景都更快。
- **从零解释**：select 使用 fd_set 且常有 FD_SETSIZE 限制；poll 使用数组；epoll 通过 create/ctl/wait 分离注册与等待。
- **底层机制**：复杂度讨论必须包含活跃比例、系统调用次数、缓存行为和 fd 数量，不能只背 O(n)/O(1)。
- **项目场景**：P3 单 socket 用 poll 足够，epoll 用于扩展统一；P5 三类长期 fd 使用 epoll 使控制流一致。
- **代码证据**：P3 `InputSocket`，P5 `addEpoll/main`。证据：`CODE`、`HOST`。
- **工程取舍**：fd 很少时可读性更重要；epoll 带来注册状态和 LT/ET 语义成本。
- **常见误区**：说 epoll 完全没有遍历；用户仍要处理返回的就绪数组。
- **30 秒回答**：epoll 的优势是兴趣集合留在内核，只返回就绪项。P5 用它统一 IIO、timerfd、signalfd；P3 当前单 socket 选择更多是架构一致性，不夸大性能。
- **2 分钟展开**：逐项比较接口、集合更新、数量限制、返回方式和适用规模。

### A07｜原题 186：epoll 生命周期与错误处理

- **一句话结论**：epoll 本身也是 fd；创建、注册、等待、删除/关闭都要纳入资源所有权，事件必须检查 ERR/HUP 和 EINTR。
- **从零解释**：`epoll_ctl(ADD)` 建立关注关系，`epoll_wait` 返回事件；被监控 fd 关闭后关系由内核处理，但应用仍需明确关闭顺序。
- **底层机制**：CLOEXEC 防止 exec 后泄漏；wait 被信号打断返回 EINTR 不一定是业务故障。
- **项目场景**：P3 析构分别关闭 epoll/socket；P5 所有 fd 用 UniqueFd，正常/异常路径一致。
- **代码证据**：P3 `InputSocket::~InputSocket`，P5 `UniqueFd`。证据：`CODE`、`HOST`。
- **工程取舍**：用 RAII 集中关闭；错误事件转换为上层状态，不在循环静默继续。
- **常见误区**：只处理 EPOLLIN；fd 默认初始化为 0 导致误关 stdin；重复 close。
- **30 秒回答**：我用 -1 表示无所有权、RAII 管 epoll 和源 fd，并处理 EINTR/ERR/HUP。创建中途失败不会留下半初始化 fd。
- **2 分钟展开**：说明 close 与 epoll interest 的关系、CLOEXEC 和 fd 复用风险。

### A08｜原题 187：LT、ET 与读到 EAGAIN

- **一句话结论**：LT 在仍就绪时持续通知；ET 通常只在状态边沿通知，因此必须使用非阻塞 fd 并循环处理到 EAGAIN。
- **从零解释**：ET 如果只读一次，缓冲区剩余数据可能没有新的边沿，再也等不到通知。
- **底层机制**：事件表示内核缓冲状态变化，不等于应用帧完成。
- **项目场景**：P5 使用 LT 但仍采用非阻塞 drain 和 pending 缓冲，能处理一次多帧与尾部半帧。
- **代码证据**：P5 `apps/conditiond.cpp` 读取循环。证据：`CODE`、`HOST`。
- **工程取舍**：LT 更容易写对；ET 可减少重复通知，但代码和公平性控制更复杂。
- **常见误区**：ET 使用阻塞 fd；遇到 EAGAIN 当错误；一次 read 等于一帧。
- **30 秒回答**：ET 必须读到 EAGAIN。我的服务即使用 LT，也按非阻塞方式 drain，并把不足 24 字节的 scan 留到下一次拼接。
- **2 分钟展开**：描述 read 返回 10、38 字节时 pending 如何形成 24 字节帧。

### A09｜短读、半包与帧解析

- **一句话结论**：字节流接口只返回当前可用字节，应用必须自己维护帧边界、剩余字节和输入上限。
- **从零解释**：read 可能少于请求、等于多帧之和或被 EINTR 打断。
- **底层机制**：内核缓冲、调度和驱动分批提交决定返回大小，不受应用结构体大小约束。
- **项目场景**：P5 `pending` 累积 IIO scan；P3 UDP 保留报文边界但仍检查截断；P2 USART ISR 自己组成固定两字节业务帧。
- **代码证据**：P5 `conditiond.cpp`、P3 `InputPCAP/getPacket`、P2 USART ISR。证据：`CODE`、`HOST`。
- **工程取舍**：固定帧简单但版本扩展弱；长度字段需验证最大值，避免内存攻击/错误。
- **常见误区**：在 TCP/IIO 上直接 `read(fd,&struct,sizeof struct)` 并假设完整。
- **30 秒回答**：我把 I/O 当字节流，pending 保存残片，只有累积满 24 字节才解码；UDP 路径则按数据报检查最小长度和截断。
- **2 分钟展开**：说明固定长度、delimiter、length-prefix 三种 framing 方案。

### A10｜`signalfd`：把信号并入事件循环

- **一句话结论**：先在线程中屏蔽信号，再用 signalfd 读取信号事件，可避免异步 signal handler 的严格函数限制。
- **从零解释**：普通 handler 可在任意指令间打断程序，能安全调用的函数很少，不能随意锁 mutex、iostream 或分配内存。
- **底层机制**：被屏蔽信号排队到 signalfd，read 返回 `signalfd_siginfo`，处理发生在正常线程控制流。
- **项目场景**：P5 把 SIGINT/SIGTERM 与 IIO/timerfd 一同注册 epoll，收到后走正常 RAII 退出。
- **代码证据**：P5 `apps/conditiond.cpp`。证据：`CODE`、`HOST`。
- **工程取舍**：Linux 特有但简化事件循环；便携程序可使用 self-pipe/eventfd 模式。
- **常见误区**：创建 signalfd 却未先 block 信号；在 handler 中调用非 async-signal-safe 函数。
- **30 秒回答**：conditiond 不在 signal handler 改复杂共享状态，而是用 signalfd 把 SIGTERM 变成普通可读事件，随后自然离开循环并由 RAII 清理。
- **2 分钟展开**：说明多线程程序应在哪个时机设置 signal mask。

### A11｜`timerfd` 与单调时钟

- **一句话结论**：timerfd 把定时事件变成 fd；超时判断应使用单调时钟，避免系统时间校准导致跳变。
- **从零解释**：读 timerfd 得到累计到期次数，不能假设每次只过期一次。
- **底层机制**：`CLOCK_MONOTONIC` 不受墙上时间手动修改影响，适合持续时间。
- **项目场景**：P5 用 timerfd 周期检查传感器超时，模拟模式另一个 timerfd 产生样本。
- **代码证据**：P5 `apps/conditiond.cpp::makeTimer`。证据：`CODE`、`HOST`。
- **工程取舍**：统一进入 epoll，避免专用定时线程；长任务可能造成多次到期累积，需要读取计数。
- **常见误区**：用 `time()` 做控制超时；不读取 timerfd 导致一直可读。
- **30 秒回答**：我的服务用 CLOCK_MONOTONIC timerfd 做超时检查，读取累计到期次数，并与设备和信号共用 epoll。
- **2 分钟展开**：比较 timerfd、POSIX timer、sleep 和 RTOS tick。

## 5. 过载、重连与离线输入

### A12｜有界队列与反压

- **一句话结论**：容量上限把无限资源风险变成可选择的过载策略；反压必须从业务价值决定阻塞、拒绝或丢旧。
- **从零解释**：短时突发可由队列吸收，持续过载无法靠容量解决。
- **底层机制**：P3 的 Block 等待 not_full，DropOldest 在锁内弹出队首并记 dropped。
- **项目场景**：LiDAR 实时链路丢旧保新；离线 PCAP 可阻塞；P4 点云保存队列最多 3 帧。
- **代码证据**：P3 `bounded_queue.h/test_bounded_queue.cpp`，P4 `save_point_data`。证据：`CODE`、`HOST`。
- **工程取舍**：新鲜度与完整性不能同时无限保证；指标让过载可见。
- **常见误区**：只写“线程安全队列”不写容量和 shutdown；把丢弃隐藏。
- **30 秒回答**：实时链路选择 DropOldest 控制延迟，离线链路可 Block；两者都必须有界并记录 dropped。
- **2 分钟展开**：结合 Little 定律解释排队时间与在途数量。

### A13｜断流重连与指数退避

- **一句话结论**：失败后立即循环重连会形成 CPU、日志和网络风暴；指数退避设上限，成功后复位。
- **从零解释**：短暂故障先快速恢复，持续故障逐渐降低尝试频率。
- **底层机制**：等待序列 250、500、1000、2000、4000、5000 ms；分成小步等待保持停止响应。
- **项目场景**：P4 RTSPCapture 使用 `ReconnectBackoff`，宿主测试覆盖增长、封顶和 reset。
- **代码证据**：P4 `reconnect_backoff.h`、`rtsp_capture.cpp`、host test。证据：`CODE`、`HOST`。
- **工程取舍**：上限避免恢复太慢；生产系统还可增加 jitter，防止多设备同步重连。
- **常见误区**：异常后无 sleep；每次失败重新创建对象却不释放旧资源。
- **30 秒回答**：RTSP 重连采用封顶指数退避，成功后 reset；等待按 50 ms 小步进行，因此 stop 不会被 5 秒整段阻塞。
- **2 分钟展开**：解释 jitter、最大次数、熔断和健康状态上报。

### A14｜PCAP/EOF 与正常生命周期

- **一句话结论**：EOF 是离线输入的正常结束状态，不应 abort；解析前必须验证捕获长度和协议偏移。
- **从零解释**：abort 跳过正常清理并生成崩溃语义，会把一次回放结束误判成程序错误。
- **底层机制**：PCAP 捕获长度可能小于原始帧长度，过滤器也可能拒绝帧。
- **项目场景**：P3 `InputPCAP::getPacket` 检查 null、截断、EOF 和过滤结果，用返回状态让上层收尾。
- **代码证据**：P3 `src/input.cc::InputPCAP`。证据：`CODE`。
- **工程取舍**：离线回放可重现输入，是网络解析测试的重要工具；真实设备性能仍需 HIL。
- **常见误区**：按固定偏移无长度检查；EOF 直接 abort；把 PCAP 通过等同实时网络通过。
- **30 秒回答**：PCAP 回放结束不是崩溃。我让输入层返回 EOF 状态并正常停止流水线，同时对每层报文偏移先做截断检查。
- **2 分钟展开**：说明 caplen、len、过滤和 loop replay 的状态设计。

## 6. 数据结构与算法边界（原题 140～159）

这些题全部纳入索引，但不包装成项目经验：

- 顺序表与链表：连续内存/随机访问与节点插入/稳定性的权衡。
