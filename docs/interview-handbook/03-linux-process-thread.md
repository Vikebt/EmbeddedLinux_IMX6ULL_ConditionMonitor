# 03｜Linux 进程、线程、同步与虚拟内存

本章对应原题 100～114、160～180、193～205 的用户态部分。主线是：**进程提供隔离，线程提供同地址空间并发，同步原语维护不变量，生命周期协议保证能够退出。**

## 1. 系统调用、进程与线程

### A01｜原题 100：系统调用和库函数

- **一句话结论**：系统调用是用户态请求内核服务的受控入口；库函数是用户态接口，可能封装系统调用，也可能完全在用户态执行。
- **从零解释**：应用不能直接操作内核对象，需通过 open/read/epoll_wait 等接口进入内核。
- **底层机制**：架构特定指令切换到内核入口，内核检查参数和权限，执行后返回；glibc 通常提供包装。
- **项目场景**：P3 调 socket/epoll，P5 调 open/read/epoll/signalfd/timerfd；`std::memcpy` 则只是用户态库函数。
- **代码证据**：P5 `apps/conditiond.cpp`。证据：`CODE`、`HOST`。
- **工程取舍**：减少无意义系统调用，但不要为了“性能”绕开正确阻塞模型；批量 read/bulk read 可降低频率。
- **常见误区**：认为 printf 一定对应一个 write；stdio 还有用户态缓冲。
- **30 秒回答**：系统调用跨用户/内核边界，库函数不一定。我的驱动服务用 epoll_wait 阻塞等待内核事件，用 read 取 IIO 数据，而状态机计算完全在用户态。
- **2 分钟展开**：说明 errno、短读、EINTR 和为什么系统调用返回成功也不代表完整业务帧。

### B01｜原题 101～103：进程状态与调度

Linux 常用状态可概括为运行/就绪、可中断睡眠、不可中断睡眠、停止和僵尸。调度算法的理论分类包括先来先服务、时间片、优先级、多级反馈；Linux 实际调度需要区分普通类与实时类。五个项目没有修改调度器，因此这些内容标为 `BASE`。

项目关联点是：阻塞在 `epoll_wait` 或条件变量的线程不占用 CPU；忙轮询会让任务保持 runnable，浪费调度资源。

### A02｜原题 104、204：进程与线程、线程栈

- **一句话结论**：进程拥有独立虚拟地址空间和资源容器；同进程线程共享代码、全局区、堆和 fd，但每个线程有自己的栈、寄存器上下文和调度状态。
- **从零解释**：线程切换通常不需要更换整个地址空间，但共享内存意味着任何未同步读写都可能竞争。
- **底层机制**：内核为每个调度实体保存上下文；线程栈映射在同一进程地址空间的不同区域。
- **项目场景**：P4 的 ROS 回调、Qt 工作线程和采集线程共享对象，因此必须用 atomic/mutex；P5 选择单线程 epoll，减少共享状态。
- **代码证据**：P4 `qnode.h/qnode.cpp`；P5 `conditiond.cpp`。证据：`CODE`、`HOST`。
- **工程取舍**：I/O 多路复用适合多个 fd；CPU 密集并行或阻塞第三方库才更需要线程池。
- **常见误区**：说线程“没有独立内存”；线程有独立栈，但栈仍在共享地址空间，错误指针可访问其他线程栈。
- **30 秒回答**：光电项目多线程共享传感器对象，所以必须同步；驱动服务把 IIO、timerfd、signalfd 放进单线程 epoll，减少线程数量和退出协调成本。
- **2 分钟展开**：比较隔离、切换成本、故障影响和通信方式。

### B02｜原题 105：内核线程和用户线程

Linux 内核线程只在内核地址空间执行，通常没有普通用户地址空间；用户线程属于进程并通过系统调用进入内核。P5 的 IIO threaded handler 是内核执行上下文，但不等同于一个由本项目创建的常驻 kthread，因此只标 `RELATED`。

## 2. 同步、数据竞争与快照

### A03｜原题 106：进程/线程同步方法

- **一句话结论**：同步手段由共享范围和语义决定：线程内常用 mutex、condition_variable、atomic；进程间可用管道、socket、共享内存配合同步对象等。
- **从零解释**：互斥保护临界区，条件变量等待状态变化，atomic 保护单对象原子操作；三者不能互相简单替代。
- **底层机制**：mutex 建立同步顺序；condition_variable 释放锁并睡眠，唤醒后重新加锁和检查谓词；atomic 按内存序约束访问。
- **项目场景**：P3 有界队列使用 mutex+condition_variable；P4 单值标志用 atomic、复合快照用 mutex。
- **代码证据**：P3 `core/bounded_queue.h`；P4 各传感器 `latest()`。证据：`CODE`、`HOST`。
- **工程取舍**：单值状态优先 atomic；跨多个字段的不变量用 mutex；消息传递能减少共享。
- **常见误区**：atomic bool 能“顺便”保护旁边结构体；condition variable 不带谓词直接 wait。
- **30 秒回答**：我的项目按不变量选同步：停止标志是独立单值，用 atomic；传感器结果包含多个相关字段，用同一 mutex 复制完整快照；队列用条件变量阻塞等待。
- **2 分钟展开**：用 GNSS 经度/纬度来自不同帧说明撕裂快照问题。

### A04｜普通 `bool`、`volatile` 和 `atomic` 的边界

- **一句话结论**：并发无同步地读写普通 bool 是 data race；volatile 仍不能修复；atomic 提供该对象的原子访问和内存序。
- **从零解释**：data race 在 C++ 内存模型中是未定义行为，问题不只是偶尔读旧值。
- **底层机制**：编译器可基于“程序没有 data race”的假设优化；atomic 操作建立规定的可见性和顺序。
- **项目场景**：P4 的 `capture_thread_flag`、`close_flag` 等改为 atomic；复杂结果没有拆成多个 atomic，而使用 mutex。
- **代码证据**：P4 `src/mainwindow/include/qnode.h`、`rtsp_capture.h`。证据：`CODE`。
- **工程取舍**：默认 `memory_order_seq_cst` 更易推理；只有测量证明必要才降低内存序。
- **常见误区**：认为 x86 “本来就原子”所以普通变量安全；语言层 UB 先于硬件直觉。
- **30 秒回答**：volatile 不建立线程同步。光电项目的停止标志用 atomic，复合结果用 mutex，因为多个字段需要作为一个快照保持一致。
- **2 分钟展开**：说明 atomic 只保护自身，发布对象时还要考虑构造完成与可见性。

### A05｜一致性快照

- **一句话结论**：读取多个相关字段时，必须在同一同步边界下取得快照，否则每个字段单独“线程安全”仍可能来自不同采样时刻。
- **从零解释**：GNSS 的纬度、经度、姿态和序号共同描述一帧；读到一半被写线程更新会产生不存在的组合。
- **底层机制**：写者和读者使用同一 mutex，读者在锁内复制，锁外处理，既保证一致性又缩短持锁时间。
- **项目场景**：P4 各传感器提供 `latest()`，QNode 取得局部 snapshot 后再做 UI/发送处理。
- **代码证据**：P4 `gnss_output.h/.cpp::latest`、`qnode.cpp`。证据：`CODE`。
- **工程取舍**：复制有成本，但结构较小且换来明确一致性；点云大对象可用 shared immutable buffer 或双缓冲进一步优化。
- **常见误区**：为每个字段设置一个 mutex/atomic；锁内进行网络发送和磁盘写入。
- **30 秒回答**：我把复合传感器结果作为整体快照，在同一 mutex 下复制到局部变量，随后释放锁再处理，避免字段跨帧又控制持锁时间。
- **2 分钟展开**：比较 mutex 快照、sequence lock、copy-on-write 和双缓冲的适用条件。

### A06｜条件变量为什么必须带谓词

- **一句话结论**：等待条件必须在锁保护下循环检查，因为可能虚假唤醒、通知先于等待或多个消费者竞争同一数据。
- **从零解释**：notify 只是提示“状态可能变化”，不是把条件本身永久保存。
- **底层机制**：`wait(lock, predicate)` 原子地释放锁并睡眠，返回时重新持锁并再次检查 predicate。
- **项目场景**：P3 `BoundedQueue::push/pop` 的谓词同时包含容量/数据和 shutdown；关闭时 notify_all。
- **代码证据**：P3 `src/lslidar_ls_driver/include/.../core/bounded_queue.h`。证据：`CODE`、`HOST`。
- **工程取舍**：shutdown 必须进入谓词，否则退出线程可能永远睡眠；notify_one/all 按等待者关系选择。
- **常见误区**：用 if 代替 while；修改条件不加锁；先销毁队列再唤醒线程。
- **30 秒回答**：条件变量不保存业务条件。LiDAR 队列把“有数据或已关闭”写进谓词，关闭时 notify_all，所以消费者能从空队列等待中退出。
- **2 分钟展开**：讲解 lost wakeup、虚假唤醒和多消费者竞争。

### A07｜原题 107、108：死锁条件与预防

- **一句话结论**：互斥、占有且等待、不可剥夺、循环等待同时成立才可能死锁；工程上通过固定锁顺序、缩小临界区、避免嵌套和超时/消息传递破坏条件。
- **从零解释**：死锁不是“线程很慢”，而是等待图中形成无法自行解除的环。
- **底层机制**：两个线程分别持有 A/B 再等待对方资源是最小环。
- **项目场景**：P2 采用单一电机写入者减少共享锁；P3 shutdown 先关闭队列唤醒等待者，再 join；P4 不在快照锁内做慢 I/O。
- **代码证据**：P2 `vControlTask`；P3 `PipelineController::stop`；P4 `latest()`。证据：`CODE`、`HOST`。
- **工程取舍**：锁层次适合多个锁；actor/单写者结构从设计上删除部分锁。
- **常见误区**：把优先级反转、活锁、饥饿都叫死锁；只靠 try_lock 隐藏设计问题。
- **30 秒回答**：我优先减少共享：小车电机只有一个写者；流水线退出时先 shutdown queue 解除等待，再 join。若必须多锁，则固定顺序且不在锁内 I/O。
- **2 分钟展开**：画资源等待图，并分别指出项目如何破坏四个条件之一。

## 3. 线程生命周期与退出协议

### A08｜`detach` 与 `join`

- **一句话结论**：detach 放弃等待和生命周期控制；对象成员线程通常应有明确 stop 协议并 join。
- **从零解释**：线程函数捕获 this 后，对象析构并不自动停止线程。
- **底层机制**：detached 线程独立继续，访问已析构成员形成 use-after-free；进程退出只是粗暴终止，并非正确清理。
- **项目场景**：P4 移除 detached spinner 和工作线程，析构时置停止标志、唤醒/等待、join，再释放设备。
- **代码证据**：P4 `QNode::~QNode`、`RTSPCapture::stop_thread`。证据：`CODE`。
- **工程取舍**：线程所有者与对象所有者对齐；若后台任务确需独立，使用进程级服务或显式共享生命周期。
- **常见误区**：认为 detach 能防止主线程阻塞；它只是让问题不可等待。
- **30 秒回答**：原 detached 线程可能在对象销毁后继续访问。重构后所有成员线程都有 stop+join，设备在 join 后释放。
- **2 分钟展开**：说明 stop flag、阻塞唤醒、join 顺序和析构异常安全。

### A09｜正确停止流水线的顺序

- **一句话结论**：先发布停止意图并解除所有阻塞，再等待线程结束，最后销毁线程依赖的对象。
- **从零解释**：只改 atomic flag 不足以唤醒正在 condition_variable/epoll/read 中阻塞的线程。
- **底层机制**：关闭队列改变谓词并 notify_all；关闭/写 eventfd 等方式解除 I/O 等待；join 建立线程结束同步。
- **项目场景**：P3 Pipeline 从下游到上游停止，queue shutdown 解除 push/pop；P4 各设备线程先 stop 再 wait。
- **代码证据**：P3 `PipelineController::stop`、`BoundedQueue::shutdown`；P4 `qnode.cpp`。证据：`CODE`、`HOST`。
- **工程取舍**：停止顺序依据数据流；下游先停止可防止继续产生副作用，但要保证上游不会永久阻塞，项目通过 shutdown 解除。
- **常见误区**：先析构 queue 再 join；只设置标志；无限等待无超时和日志。
- **30 秒回答**：退出协议不是一个 bool。LiDAR 先 shutdown 队列唤醒等待者，再按数据流停止并 join，最后资源析构。
- **2 分钟展开**：画出 producer→queue→consumer 的停止时序和不同顺序的风险。

## 4. 虚拟内存与地址

### B03｜原题 109～114、172、203：地址、MMU 与虚拟内存

需要区分：

- 虚拟地址：进程看到的地址，由页表映射。
- 物理地址：内存控制器看到的地址。
- 总线地址/DMA 地址：设备发起访问时使用，可能经过 IOMMU 或平台转换。
- 页表和 TLB：页表保存映射，TLB 缓存近期转换。

虚拟内存提供隔离、按需分配、共享映射和比物理内存更灵活的地址空间。P5 的 Linux 用户程序只能通过设备文件/sysfs 访问驱动，不能把设备树物理地址直接当用户指针。项目没有实现页表或 DMA，因此标 `BASE/RELATED`。

### B04｜原题 173～179：fork、exec、父子进程与僵尸

`fork` 创建逻辑子进程，通常通过写时复制共享物理页；`exec` 用新程序映像替换当前进程；子进程退出后父进程未 wait 会留下僵尸记录。当前五项目没有用 fork/exec 构建进程模型，不能包装为项目能力。

P5 部署为 systemd 服务，进程监督交给 systemd，而不是应用自行 double-fork 守护化。这个选择可以作为现代 Linux 服务管理的工程说明。

### B05｜原题 102：Linux IPC

管道/命名管道适合字节流；Unix domain socket 支持双向与 fd 传递；消息队列保留消息边界；共享内存吞吐高但同步最复杂；信号适合有限通知。当前项目主要使用线程内同步、ROS topic 和网络 socket，未直接实现 POSIX 共享内存或 System V IPC，标为 `RELATED`。

## 5. 用户态故障定位

### A10｜原题 160：段错误和程序跑飞怎样定位

- **一句话结论**：先保存现场和可复现输入，再从 core/backtrace、日志、sanitizer 和资源指标逐层缩小，不靠猜。
- **从零解释**：段错误只说明非法内存访问被 MMU 捕获，根因可能是越界、悬空、栈溢出、竞态或 ABI 不一致。
- **底层机制**：core dump 保存寄存器和内存映像；带符号二进制可把地址还原到调用栈。
- **项目场景**：P4 原生命周期风险和别名强转都可能产生偶现故障；重构用 join、mutex snapshot 和 memcpy 降低 UB。
- **代码证据**：P4 `INTERVIEW_EVIDENCE.md` 和相关实现。证据：`CODE`；未制造真实 core，故为 `RELATED` 调试流程。
- **工程取舍**：开发构建保留 `-g`，测试启用 ASan/UBSan；目标机资源有限时可离线分析 core。
- **常见误区**：只看最后一条日志；优化构建无符号；复现前就修改多个地方。
- **30 秒回答**：我会固定版本和输入，启用 core，使用 gdb bt/thread apply all bt；内存类问题再用 ASan/Valgrind，竞态用 TSan 或同步审查，并对 fd/内存趋势做长稳观察。
- **2 分钟展开**：按“复现→现场→最小化→假设→验证”描述调试闭环。

### B06｜原题 161～168：命令、编译、库和链接

- `gcc -E/-S/-c/link` 对应预处理、编译、汇编和链接。
- 静态库内容复制进入最终产物；动态库在加载/运行时解析，减小重复但引入版本和部署依赖。
- make 根据目标、依赖和命令决定增量构建；CMake 生成具体构建系统，不是编译器。
- 软链接保存路径，硬链接增加同一 inode 的目录项。

P5 的 ARM 工具链文件与 `file` 输出是交叉编译证据；P3/P4 的 ROS/catkin 依赖说明动态库版本是部署风险。

### A11｜原题 169、170：文件描述符与 inode

- **一句话结论**：fd 是进程文件描述符表中的整数索引，指向内核打开文件描述；inode 表示文件对象元数据，目录项把名字映射到 inode。
- **从零解释**：socket、epoll、timerfd、signalfd 和 IIO 设备都可以表现为 fd，因此能统一进入事件循环。
- **底层机制**：dup/fork 可让多个 fd 指向同一打开文件描述，共享偏移/状态的细节需区分。
- **项目场景**：P5 用 fd 统一设备、时钟、信号；P3 管理 UDP socket 与 epoll fd。
- **代码证据**：P5 `UniqueFd`、P3 `InputSocket`。证据：`CODE`、`HOST`。
- **工程取舍**：用 `-1` 表示无所有权，设置 CLOEXEC，异常路径也关闭。
- **常见误区**：fd 等于文件；close 一个重复 fd 会自动关闭所有引用。
- **30 秒回答**：fd 是进程表索引，不只代表磁盘文件。我的服务把 IIO、timerfd、signalfd 都注册进 epoll，并用 UniqueFd 管理关闭责任。
- **2 分钟展开**：说明 file description、inode、dentry 和设备 file_operations 的关系。

### A12｜原题 171：`/proc/<pid>` 能看什么

- **一句话结论**：`/proc/<pid>` 是内核导出的进程运行视图，可检查 maps、status、fd、task 和调度/内存状态。
- **从零解释**：数字目录名就是 PID；内容不是普通持久文件，而是读取时由内核生成。
- **底层机制**：`fd/` 软链接可观察打开资源，`maps` 查看映射，`status` 查看线程和内存概要。
- **项目场景**：P3/P4/P5 长稳时可采样 fd 数、线程数和 RSS，验证重连/启动停止是否泄漏。
- **代码证据**：属于验证方法 `RELATED`，当前仓库未提交长期曲线。
- **工程取舍**：轻量现场先用 proc，复杂内存问题再用 profiler/sanitizer。
- **常见误区**：把 VIRT 当实际物理占用；忽略共享页和缓存。
- **30 秒回答**：我会比较 `/proc/pid/fd`、`task` 和 `status` 的时间序列，判断断流重连后是否持续增长，再结合日志定位创建路径。
- **2 分钟展开**：说明 smaps、fdinfo 和 limits 的用途。

### A13｜原题 180：管程思想

- **一句话结论**：管程把共享状态、互斥和条件等待封装成一组操作，使调用者不能绕开同步协议。
- **从零解释**：它不是某个单独 Linux API，而是一种结构化并发抽象。
- **底层机制**：同一时刻一个执行流进入受保护操作；条件变量等待状态谓词。
- **项目场景**：P3 `BoundedQueue` 封装队列、mutex、两个 condition_variable 和 shutdown，不让调用者直接碰内部 deque。
- **代码证据**：P3 `core/bounded_queue.h`。证据：`CODE`、`HOST`。
- **工程取舍**：封装增加少量接口代码，但把不变量集中，远好于散落的共享容器和外部锁。
- **常见误区**：把管程等同于 mutex；缺少条件谓词和封装边界。
- **30 秒回答**：LiDAR 的 BoundedQueue 就是管程式封装：队列状态、锁、条件变量和关闭协议在同一类中，外部只能 push/pop/shutdown。
- **2 分钟展开**：列出容量、关闭后唤醒、丢弃计数这些类不变量。

## 6. 本章概念辨析

| 概念 | 核心区别 | 项目落点 |
| --- | --- | --- |
| 进程 vs 线程 | 地址空间隔离 vs 共享地址空间调度实体 | P4 多线程、P5 单进程事件循环 |
