# 02｜ARM、中断与 FreeRTOS 实时设计

本章对应原题 72～99，重点不是背寄存器数量，而是理解一条实时链路：**硬件事件到达 → 中断快速记录 → RTOS 原语交接 → 任务处理 → 有界超时与故障恢复。**

## 1. ARM 与异常基础

### B01｜原题 72～74：ARM 寄存器、状态寄存器与架构差异

ARM 寄存器数量必须先说明架构和工作模式，不能脱离 Cortex-M3、ARMv7-A 或 ARMv8-A 给单一数字。STM32F103 使用 Cortex-M3，异常入口由硬件自动压栈部分上下文；I.MX6ULL 使用 Cortex-A7，运行 Linux，涉及 MMU、特权级和更完整的进程上下文。

项目真正相关的是：P1/P2 依赖 Cortex-M 异常模型和 FreeRTOS 端口；P5 依赖 ARM Linux 交叉编译。ARMv8 的 AArch64、异常级别等不是当前硬件的直接实现，标记为 `RELATED`。

### A01｜原题 75、76：中断产生、向量和嵌套

- **一句话结论**：中断是硬件事件打断正常控制流，处理器保存最小上下文、查向量进入 ISR，退出时恢复现场；嵌套由优先级与屏蔽状态决定。
- **从零解释**：外设置位状态并向 NVIC 请求，NVIC 仲裁后处理器进入异常。向量表保存各异常入口地址。
- **底层机制**：Cortex-M 硬件自动压栈 R0-R3、R12、LR、PC、xPSR；高优先级中断可以抢占低优先级中断，具体还受优先级分组影响。
- **项目场景**：P2 的 USART1 接收中断读取字节并通知任务；P1 的 SVC 向量必须正确转交 FreeRTOS 端口，才能启动首任务。
- **代码证据**：P2 `Core/stm32f10x_it.c::USART1_IRQHandler`；P1 `Core/stm32f10x_it.c::SVC_Handler`。证据：`CODE`。
- **工程取舍**：ISR 只做确定、短小、不可阻塞的工作；复杂状态机留给任务。
- **常见误区**：把中断向量说成“中断号”；认为函数调用也会由硬件自动保存同样上下文。
- **30 秒回答**：以小车 USART 为例，外设触发 NVIC 后进入向量表对应 ISR，ISR 只收字节和发 FromISR 队列；业务判断由控制任务完成。这样减少中断占用和系统抖动。
- **2 分钟展开**：画出外设标志、NVIC、自动压栈、ISR、PendSV/SVC 与任务切换关系。

### A02｜原题 77、80、83：ISR 的能力边界

- **一句话结论**：中断响应快，但会增加延迟和抢占复杂度；ISR 没有普通调用者，不能依赖返回值传业务结果，也不能调用可能阻塞或不可重入的接口。
- **从零解释**：ISR 在特殊上下文运行，调度器和库函数对其有额外限制。
- **底层机制**：`printf` 可能持锁、动态分配或等待串口；在 ISR 中调用会造成死锁、长延迟或重入破坏。
- **项目场景**：P2 ISR 不做 OLED、printf、病房匹配或电机控制，只形成两字节帧并 `xQueueOverwriteFromISR`。
- **代码证据**：P2 `Core/stm32f10x_it.c`。证据：`CODE`。
- **工程取舍**：调试中断使用环形 trace、计数器或把事件发给日志任务；异常紧急信息也要采用 ISR-safe 路径。
- **常见误区**：说“ISR 完全不能有参数/返回值”而忽略 C 函数签名与硬件入口的区别；真正约束是业务不能依靠普通调用协议。
- **30 秒回答**：ISR 的关键是快和可预测。小车中断只组帧、覆盖最新值队列并请求调度，所有可能阻塞或耗时的操作都移到任务。
- **2 分钟展开**：说明 `pxHigherPriorityTaskWoken`、`portYIELD_FROM_ISR` 和为什么普通 RTOS API 不能在 ISR 使用。

### A03｜原题 78、79：软中断与函数调用的区别

- **一句话结论**：软中断/软件触发异常改变执行上下文和优先级，由异常机制调度；普通函数调用仍在当前上下文和调用栈连续执行。
- **从零解释**：函数调用是同步控制转移；软件异常可用于特权切换、系统服务或延迟处理。
- **底层机制**：P1 的 SVC 用异常返回机制恢复首任务上下文；PendSV 通常承担 Cortex-M RTOS 上下文切换。
- **项目场景**：P1 原空 `SVC_Handler` 会破坏 FreeRTOS 启动链，重构后转到 `vPortSVCHandler`。
- **代码证据**：P1 `Core/stm32f10x_it.c::SVC_Handler`、FreeRTOS port。证据：`CODE`。
- **工程取舍**：应用层不直接滥用软中断；交给 RTOS 端口实现架构相关上下文切换。
- **常见误区**：把 Linux softirq、Cortex-M SVC 和“软件调用一个 ISR 函数”混为一谈。
- **30 秒回答**：普通函数不会改变特权和异常上下文；SVC 是架构异常。体温仪必须把 SVC 交给 FreeRTOS 端口，首任务才会按异常返回恢复上下文。
- **2 分钟展开**：对比 SVC、PendSV、SysTick 的职责，再说明 Linux softirq 是另一套概念。

### A04｜原题 81、82：主循环/任务与中断共享数据

- **一句话结论**：volatile 只能保证访问不被省略；共享对象还需要原子性、一致性和可重入设计，最佳方案通常是消息传递。
- **从零解释**：ISR 可以在任务读到一半时改写多字节对象；同一函数若使用静态缓冲或非重入外设，也可能被中断重入。
- **底层机制**：Cortex-M 对某些自然对齐字宽访问是单指令，但复合操作和结构体更新仍不是原子事务。
- **项目场景**：P2 用 FromISR 队列把完整视觉帧交给任务；P1 用队列传温度/RFID，而不是让任务轮询裸全局结构体。
- **代码证据**：P2 `xQueueOverwriteFromISR`，P1 `prvSendLatest`。证据：`CODE`、`HOST`。
- **工程取舍**：简单单字标志可用临界区/原子；数据帧优先队列；共享外设用 mutex，但 ISR 不能拿普通 mutex。
- **常见误区**：给整个结构体加 volatile 就认为快照一致；在 ISR 调用使用 mutex 的 I2C 函数。
- **30 秒回答**：我的项目尽量不让 ISR 与任务共享可变结构。ISR 形成完整消息，通过 FromISR 队列交接；这样同步点和数据所有权都更清楚。
- **2 分钟展开**：举出撕裂读取、读改写竞争和函数重入三个不同问题。

## 2. 实时系统与 FreeRTOS

### A05｜原题 86：实时系统与通用 Linux 的区别

- **一句话结论**：实时性的核心是截止时间和最坏响应上界，不是平均速度快；普通 Linux 优先吞吐和公平，RTOS 更强调可预测调度。
- **从零解释**：硬实时错过期限即失败，软实时偶发超时只降低质量。FreeRTOS 不是自动实时，设计不当仍会长时间关中断或阻塞。
- **底层机制**：抢占优先级、临界区长度、中断延迟、锁和最坏执行时间共同决定响应。
- **项目场景**：P2 电机控制和视觉事件要求及时但当前没有硬截止时间测量；P3 LiDAR 关注有界延迟，通过 DropOldest 避免积压。
- **代码证据**：P2 非阻塞 FSM；P3 `BoundedQueue`。证据：`CODE`、`HOST`，实时上界为 `TODO-HIL`。
- **工程取舍**：用有界队列和超时建立可分析性；不把“用了 FreeRTOS”写成“满足硬实时”。
- **常见误区**：把实时等同于高主频；把 Linux 一概说成不能实时。
- **30 秒回答**：实时看最坏响应而不是平均性能。小车重构减少 ISR 工作和阻塞 delay，LiDAR 用丢旧控制排队延迟，但没有硬件时序测量，所以只声称结构上改善可预测性。
- **2 分钟展开**：说明 PREEMPT_RT、优先级、WCET 和测量方法。

### A06｜原题 87：FreeRTOS 配置与中断优先级

- **一句话结论**：必须配置时钟、最大优先级、可调用 RTOS API 的中断优先级边界、堆、栈检查和 hook；数值优先级与逻辑高低要分清。
- **从零解释**：Cortex-M 数值越小优先级越高。高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断不能调用 FreeRTOS API。
- **底层机制**：RTOS 通过 BASEPRI 屏蔽一部分中断保护内核临界区，最高紧急中断仍可响应但不得碰内核对象。
- **项目场景**：P1/P2 使用 FromISR API、启用 malloc failed 和 level-2 stack overflow hook，并对创建结果断言。
- **代码证据**：两个 STM32 项目的 `FreeRTOSConfig.h`、`Core/main.c`。证据：`CODE`。
- **工程取舍**：中断优先级规划写入系统设计，不在各驱动随意设置；创建失败应在启动阶段显式停机/报警。
- **常见误区**：把 library priority 和寄存器移位后的 priority 混用；所有中断都设最高。
- **30 秒回答**：配置重点不仅是 tick，还包括可调用内核 API 的中断优先级边界。项目中 ISR 使用专用 API，任务/队列创建立即断言，并启用堆耗尽和栈溢出 hook。
- **2 分钟展开**：解释 BASEPRI 和 `configPRIO_BITS`，再讲如何审查每个 NVIC priority。

### A07｜原题 88：优先级反转

- **一句话结论**：高优先级任务等待低优先级任务持锁，而中优先级任务不断抢占低优先级任务，会形成优先级反转；mutex 的优先级继承只能缓解特定情况。
- **从零解释**：真正阻塞高任务的并不是低任务执行时间本身，而是低任务无法获得 CPU 释放资源。
- **底层机制**：优先级继承临时提升持锁者；释放 mutex 后恢复。二值信号量通常没有所有者与继承语义。
- **项目场景**：P1 I2C 总线使用 mutex，临界区只复制短小共享数据，不把 RTC/I2C 轮询包进去。
- **代码证据**：P1 `Core/main.c` 的 I2C mutex 与短临界区。证据：`CODE`。
- **工程取舍**：减少锁持有时间、避免嵌套锁、使用单一所有者任务，通常比依赖继承更稳。
- **常见误区**：把任务切换都叫优先级反转；认为提高高任务优先级能解决。
- **30 秒回答**：我用 mutex 串行化 I2C，但把慢 I/O 放在临界区外。mutex 可做优先级继承，不过设计重点仍是缩短持锁时间和减少共享资源。
- **2 分钟展开**：画出 L 持锁、H 阻塞、M 抢占的时间线，并区分反转、死锁和饥饿。

### A08｜原题 89：FreeRTOS 任务调度

- **一句话结论**：调度器选择最高优先级就绪任务；同优先级可时间片轮转，任务通过阻塞等待事件释放 CPU。
- **从零解释**：任务常见状态为运行、就绪、阻塞和挂起。延时、队列等待和信号量等待应进入阻塞态，而不是忙等。
- **底层机制**：SysTick 提供时基，PendSV 完成上下文切换，SVC 启动首任务。
- **项目场景**：P1 修正 SVC；P2 控制 FSM 周期执行、传感器任务有界等待；不再用长 delay 完成整个动作。
- **代码证据**：P1 `SVC_Handler`；P2 `CartState_Step`。证据：`CODE`、`HOST`。
- **工程取舍**：周期任务用 `vTaskDelayUntil` 更利于稳定周期；事件任务用阻塞队列，不轮询。
- **常见误区**：认为优先级越高越实时；高优先级忙循环会饿死系统。
- **30 秒回答**：FreeRTOS 每次运行最高优先级就绪任务。项目中事件通过队列唤醒，状态机周期推进；SVC/PendSV 属于端口层，不在业务里自己切上下文。
- **2 分钟展开**：说明抢占、时间片、tickless 可选项和任务状态转移。

### A09｜原题 90：FreeRTOS IPC 怎么选

- **一句话结论**：队列传数据，信号量传事件/计数，mutex 保护有所有者的资源，事件组表达多个布尔条件，任务通知适合轻量一对一通知。
- **从零解释**：选择同步原语前先回答“传不传数据、是否有所有者、能否丢、谁唤醒谁”。
- **底层机制**：队列复制固定大小 item；mutex 带所有权；通知存放在 TCB 内，开销小但耦合一对一。
- **项目场景**：P1/P2 传感器使用队列，I2C 使用 mutex；“最新值”数据使用长度 1 mailbox/overwrite。
- **代码证据**：P1 `prvSendLatest`，P2 `xQueueOverwrite`。证据：`CODE`、`HOST`。
- **工程取舍**：关键命令不能静默 overwrite；传感器最新值可以丢旧。同步语义必须与业务语义一致。
- **常见误区**：用 binary semaphore 保护资源却期待优先级继承；把全局变量和信号量分开导致数据/事件错位。
- **30 秒回答**：我的选择先看语义。体温和视觉帧只关心最新值，用长度 1 队列；I2C 有明确资源所有者，用 mutex；状态机命令由单控制任务消费。
- **2 分钟展开**：给出 queue/semaphore/mutex/event group/notification 决策表。

### A10｜队列满与最新值邮箱（原题 90 的项目追问）

- **一句话结论**：队列容量是资源上限，满时必须显式选择阻塞、拒绝新值或丢弃旧值；最新值语义适合传感器状态，不适合交易命令。
- **从零解释**：如果生产速度长期高于消费速度，无界队列只会把故障推迟成内存耗尽和高延迟。
- **底层机制**：长度 1 overwrite 始终保留最近完整样本；P1 的 `prvSendLatest` 在普通队列满时先取出最旧再重试。
- **项目场景**：P1 温度/RFID、P2 视觉帧/重量强调新鲜；P3 LiDAR 点云流水线使用 DropOldest 并统计 dropped。
- **代码证据**：P1 `Core/main.c::prvSendLatest`；P2 `xQueueOverwrite`；P3 `BoundedQueue`。证据：`CODE`、`HOST`。
- **工程取舍**：丢旧换有界延迟，但必须有丢弃计数和业务确认；离线完整处理则可 Block。
- **常见误区**：只增大队列，不分析持续过载；丢数据却没有指标。
- **30 秒回答**：实时传感器链路更怕旧数据积压，因此我选择丢旧保新；离线处理才允许阻塞。策略和 dropped 指标必须一起设计。
- **2 分钟展开**：用到达率、服务率和排队延迟解释为什么“更大队列”不等于修复。

### A11｜非阻塞有限状态机

- **一句话结论**：把长动作拆成状态、事件和进入时间，每次调用只推进一步，使任务持续响应新输入和故障。
- **从零解释**：连续 delay 会占住该任务的业务流程，即使调度器能运行其他任务，这个控制逻辑也无法处理新事件。
- **底层机制**：状态保存跨调用上下文，`now - entered` 判断超时，输出由当前状态唯一决定。
- **项目场景**：P2 的转向、提示、掉头和送达流程由 `CartState_Step` 推进，电机只有控制任务一个写入者。
- **代码证据**：P2 `APP/cart_control/cart_state.c`、`Core/main.c::vControlTask`。证据：`CODE`、`HOST`。
- **工程取舍**：状态数增加但可测试、可中断；小动作仍可短延时，但不能影响故障响应要求。
- **常见误区**：把 switch 写法当状态机，却没有明确事件、进入/退出动作和非法状态处理。
- **30 秒回答**：我把小车转向从阻塞 delay 改成时间驱动 FSM，控制任务是电机唯一写者；测试直接输入时间和传感器状态，验证每次输出。
- **2 分钟展开**：画出 FOLLOW→TURN→RECOVER 等状态及超时边。

### A12｜Tick 回绕

- **一句话结论**：用同宽无符号差值判断经过时间，可以自然处理计数器回绕；不要比较绝对 tick 大小。
- **从零解释**：固定宽度无符号算术按模运算，`now - start` 在一次回绕后仍得到正确短间隔。
- **底层机制**：前提是目标时间间隔小于可无歧义表示的范围，通常要求不超过计数周期的一半。
- **项目场景**：P2 `prvElapsed` 和宿主测试覆盖 `UINT32_MAX` 附近进入状态后的回绕。
- **代码证据**：P2 `APP/cart_control/cart_state.c::prvElapsed`、`tests/host/test_cart_state.c`。证据：`CODE`、`HOST`。
- **工程取舍**：统一使用单调 tick 做持续时间；日历时间用于展示，不用于控制超时。
- **常见误区**：`if (now >= deadline)` 在回绕附近失败；有符号转换引入未定义/实现相关行为。
- **30 秒回答**：小车状态超时用 `(uint32_t)(now-start) >= duration`，宿主测试从最大值跨回零验证，因此不依赖绝对 tick 排序。
- **2 分钟展开**：举 `start=0xfffffff0, now=0x10` 的模减法例子。

### A13｜传感器等待为什么必须超时

- **一句话结论**：任何依赖外部设备电平、串口或网络的数据等待都必须有上界，否则一个故障外设可永久占住任务。
- **从零解释**：忙等直到 DOUT 改变，在传感器断线时永远不返回，上层无法进入降级或错误状态。
- **底层机制**：超时把“永久等待”变成显式错误返回，错误才能沿调用链传播。
- **项目场景**：P2 HX711 DOUT 等待加入 100 ms 超时，采样结构带 valid 标志，界面显示 fault。
- **代码证据**：P2 `APP/hx711/hx711.c::HX711_Read`、`Core/main.c`。证据：`CODE`；真实断线为 `TODO-HIL`。
- **工程取舍**：超时值要基于器件转换时间和调度抖动；过短产生误报，过长拖慢恢复。
- **常见误区**：只在最外层加看门狗，不让驱动返回可诊断错误。
- **30 秒回答**：HX711 等待现在有 100 ms 上限，失败通过 valid 状态交给任务，而不是把整个传感器任务卡死。
- **2 分钟展开**：说明超时、重试、退避和系统看门狗分别解决不同层级的问题。

### B02｜原题 91～99：接口、存储结构与流水线

- SPI、I2C、UART 的选择取决于拓扑、速率、引脚、全双工、寻址和距离。P1/P2 使用 MCU 外设，P5 使用 SPI IMU。
- Harvard/Von Neumann、RISC/CISC、流水线、Cache 和存储层次属于理解 ARM 的基础，但项目没有修改 CPU 微架构，标为 `BASE/RELATED`。
- NOR/NAND、SRAM/DRAM/SDRAM 的区别要从随机访问、擦写粒度、是否刷新和典型用途回答，不要仅背“谁快”。

## 3. 错误演化案例

### 案例一：ISR 里直接控制电机

```text
串口中断执行病房匹配和转向
    ↓
ISR 执行时间随业务分支变化
    ↓
更高频串口/定时器中断延迟
    ↓
电机由 ISR 与任务共同写入
    ↓
输出顺序依赖抢占时机，故障难复现
```

P2 的修复是 ISR 只发布帧，控制任务成为唯一电机写入者。

### 案例二：队列无限变大

```text
生产速度持续高于消费速度
    ↓
队列等待时间增加
    ↓
系统处理的是越来越旧的数据
    ↓
内存耗尽或控制响应失效
```

P1/P2/P3 根据实时数据新鲜度选择 overwrite/DropOldest，并保留过载可观测性。
