# 01｜C/C++、内存与资源生命周期

本章对应原题 1～71。A 级题不追求背完标准条款，而是建立一条主线：**对象存在哪里、谁拥有它、谁可以并发访问、什么时候失效、失败路径怎样释放资源。**

## 1. 编译单元、链接与限定符

### A01｜原题 4：什么时候使用 `const`？

- **一句话结论**：`const` 是接口契约，限制“通过当前表达式修改对象”，但不自动解决并发同步，也不保证底层对象永远不变。
- **从零解释**：`const int *p` 表示不能通过 `p` 修改所指值；`int * const p` 表示指针本身不能改指向；成员函数后的 `const` 表示不能通过该函数修改非 `mutable` 成员。
- **底层机制**：编译器据类型系统拒绝非法写入；常量是否放进只读段取决于存储期、链接和实现。用强制转换写入本来就是 const 的对象会产生未定义行为。
- **项目场景**：P5 的 `Monitor::update(const Sample& sample)` 用只读引用表达输入样本不会被算法修改；P3 的队列查询和 P4 的 `latest()` 也用 const 成员函数表达只读快照。
- **代码证据**：`libcondition/src/condition_monitor.cpp::Monitor::update`，`src/mainwindow/include/gnss_output.h::latest`。证据：`CODE`、`HOST`。
- **工程取舍**：传大对象使用 `const&` 避免复制；小标量直接传值通常更简单。不要为了“性能”把所有参数都改成引用。
- **常见误区**：把 const 当作线程安全；返回指向内部可变缓存的 const 指针仍可能因其他线程修改而失效。
- **30 秒回答**：const 主要表达接口只读约束。项目中采样输入和快照读取使用 const 引用或 const 成员函数，既避免无谓复制，也让调用者知道函数不会经该接口修改对象；但并发一致性仍由 mutex/atomic 保证。
- **2 分钟展开**：继续说明顶层/底层 const、const 成员函数、逻辑 const，以及为什么 mutex 常声明为 `mutable` 以允许 const 查询函数加锁。

### B01｜原题 1～3：`static`、`extern`、`extern "C"`

`static` 在文件作用域提供内部链接，在函数局部让对象拥有静态存储期，在类中表示成员属于类型。`extern` 只声明符号在其他翻译单元定义，不分配新的定义；`extern "C"` 改变语言链接，常用于 C++ 调用 C 驱动接口，主要解决名字改编，不等于“按 C 语法编译函数体”。

五项目中大量 STM32 BSP 头文件采用 C 接口，Linux C++ 应用链接 C 系统调用和第三方 C 库。当前项目没有专门封装跨语言 ABI，因此标为 `RELATED`，不要说成自己设计了 C ABI。

### A02｜原题 6、7：`volatile` 的作用与正确用法

- **一句话结论**：volatile 要求对该对象的访问按抽象机可观察规则发生，适合内存映射寄存器；它不提供原子性、互斥或线程间 happens-before。
- **从零解释**：硬件可以在程序不知道的时刻改变寄存器。若编译器把读取缓存到普通寄存器，循环可能永远看不到变化，因此寄存器声明需要 volatile。
- **底层机制**：volatile 约束编译器优化，不会自动生成锁，也不能保证 `counter++` 不被打断。CPU 缓存一致性和 C++ 内存序是另一层问题。
- **项目场景**：P1/P2 通过 CMSIS 的 volatile 寄存器定义访问 GPIO、USART；P4 的跨线程停止标志使用 `std::atomic<bool>`，而不是 volatile。
- **代码证据**：STM32 `Libraries/CMSIS` 寄存器类型；P4 `src/mainwindow/include/qnode.h` 中 atomic 标志。证据：`CODE`。
- **工程取舍**：硬件寄存器用 volatile；线程通信用 atomic/mutex；ISR 与任务共享复合数据优先用 RTOS 队列，而不是裸全局变量。
- **常见误区**：说“volatile 每次从内存读，所以线程安全”；在单核 MCU 上误以为禁止编译器优化就等于不可中断。
- **30 秒回答**：volatile 解决编译器不能假设对象不变的问题，典型是硬件寄存器。它不解决竞争，所以多线程标志在光电项目里用 atomic，复合结果用 mutex；STM32 ISR 到任务的数据用 FromISR 队列传递。
- **2 分钟展开**：区分可见性、原子性和有序性，并举 `volatile uint32_t x; x++` 仍是读—改—写三个阶段的例子。

### A03｜原题 14、50：绝对地址和硬件寄存器访问

- **一句话结论**：把固定地址转换成指向正确宽度的 volatile 指针，再通过受控接口访问；地址、宽度、对齐和访问属性都必须来自芯片手册。
- **从零解释**：MCU 外设寄存器映射到地址空间，读写该地址会触发外设行为，而不是访问普通 RAM。
- **底层机制**：总线矩阵把地址译码到外设；访问宽度错误可能触发总线错误或误写相邻寄存器。读清零、写 1 清零等语义还要求按手册操作。
- **项目场景**：P1/P2 使用 STM32 标准外设库/CMSIS，不在业务层散落魔法地址；P5 使用 regmap 把 SPI 寄存器协议集中封装。
- **代码证据**：STM32 `Libraries/CMSIS`，P5 `kernel/icm20608_iio.c::icm20608_regmap_config`。证据：`CODE`。
- **工程取舍**：优先使用芯片厂商定义和驱动框架；只有启动代码或极底层 BSP 才直接操作绝对地址。
- **常见误区**：遗漏 volatile、使用错误整数宽度、忽略对齐、把 CPU 内存映射 I/O 和 SPI 芯片内部寄存器混为一谈。
- **30 秒回答**：MCU 的 MMIO 可用指向固定地址的 volatile 指针访问，但项目里优先用 CMSIS；SPI IMU 不是 CPU 直接寻址，必须经 SPI 控制器，驱动中用 regmap 表达寄存器和值宽度。
- **2 分钟展开**：比较 MMIO、port I/O 和外部总线寄存器，并解释为什么 Linux 用户态不能随意解引用物理地址。

## 2. 内存区域、栈堆与分配

### A04｜原题 21：C/C++ 程序的内存分区

- **一句话结论**：常见进程映像包含代码、只读数据、已初始化数据、BSS、堆、映射区和各线程栈；MCU 链接脚本则把这些段映射到 Flash/RAM。
- **从零解释**：源代码中的对象根据存储期和链接属性进入不同段。局部自动对象通常在栈，动态对象来自堆，但优化后未必真的落内存。
- **底层机制**：编译器产生段，链接器布局，加载器或启动代码把数据搬到目标位置并清零 BSS。
- **项目场景**：P1/P2 的任务栈和 FreeRTOS heap 都占有限 SRAM；P3～P5 的 Linux 进程由虚拟内存管理，线程各有栈但共享堆。
- **代码证据**：P1/P2 `FreeRTOSConfig.h`、`heap_4.c` 和任务创建栈深；P5 CMake 产物经 ARM ELF 检查。证据：`CODE`、`CROSS`。
- **工程取舍**：MCU 避免大局部数组和频繁动态分配；Linux 仍要明确所有权，但不必把堆一概视为禁用。
- **常见误区**：把“代码段只读”说成所有 const 都在代码段；把线程栈和进程栈当成同一块。
- **30 秒回答**：MCU 更关注 Flash/RAM 段和任务栈预算，Linux 更关注虚拟地址空间与每线程栈。五项目中 RTOS 创建后立即断言，Linux 侧用 RAII 管理动态资源。
- **2 分钟展开**：画出 `.text/.rodata/.data/.bss/heap/stack`，再说明 ELF 与链接脚本/加载器的关系。

### A05｜原题 22、23：堆、栈和大局部数组

- **一句话结论**：栈分配快且自动回收，但容量有限；大局部数组会直接消耗当前线程/任务栈，在 MCU 上尤其危险。
- **从零解释**：每次函数调用建立栈帧，局部数组的大小会计入栈帧。FreeRTOS 每个任务有独立栈，溢出可能破坏相邻内存。
- **底层机制**：栈指针移动完成分配；没有逐对象边界检查时，越界可能直到异常或数据损坏才暴露。
- **项目场景**：P1/P2 开启 level-2 栈溢出 hook，并为任务指定栈深；P5 的 IIO scan 是固定小对象，点云等大对象不放线程栈。
- **代码证据**：P1 `Core/main.c::vApplicationStackOverflowHook`、`FreeRTOSConfig.h`；P2 任务创建。证据：`CODE`。
- **工程取舍**：固定小缓冲可放栈；大或生命周期长的缓冲使用静态区、专用内存池或受所有权管理的堆，并做上限。
- **常见误区**：认为“2048 字节一定不大”；真正标准取决于任务栈预算、调用深度、中断嵌套和 ABI。
- **30 秒回答**：大局部数组是否安全取决于当前栈预算。STM32 每个 FreeRTOS 任务栈很小，所以我启用栈溢出检查，并避免在深调用链创建大缓冲。
- **2 分钟展开**：说明高水位监控、最坏调用深度和中断栈的区别。

### A06｜原题 25、29：`malloc/free` 与 `new/delete`

- **一句话结论**：malloc 管理原始字节，new 同时分配并构造对象；delete 析构并释放。二者不可交叉配对。
- **从零解释**：C++ 对象可能有构造不变量和析构动作，因此仅得到一块内存并不等于对象已经建立。
- **底层机制**：new 表达式通常调用 `operator new` 后执行构造；delete 先执行析构再调用 `operator delete`。数组版本还要正确处理多个元素。
- **项目场景**：P3/P4 的 C++ 对象交由容器、栈对象或明确智能指针管理；P5 的 fd 不用 new，而用值类型 RAII 包装。
- **代码证据**：P5 `apps/conditiond.cpp::UniqueFd`；P4 各线程对象的析构/stop。证据：`CODE`。
- **工程取舍**：优先值语义与 `make_unique`；只有确需共享生命周期才使用 shared_ptr。MCU 实时路径避免不可控分配。
- **常见误区**：`free(new T)`、`delete malloc()`、忘记虚析构、把 placement new 当普通分配。
- **30 秒回答**：malloc/free 只处理字节，new/delete还处理对象生命周期。项目中我尽量用值语义和 RAII，让异常路径不需要手写多套释放代码。
- **2 分钟展开**：补充失败行为、`nothrow`、operator new 可重载以及数组 delete 的配对要求。

### A07｜原题 32：内存泄漏如何检测与避免

- **一句话结论**：泄漏的根因是所有权或退出路径不清，而不只是“忘记 free”；避免优先于事后工具检测。
- **从零解释**：进程仍持有无法再使用的内存、fd、线程或内核对象，都属于资源泄漏的工程问题。
- **底层机制**：异常、早返回、构造一半失败和线程未 join 是最常见的分支遗漏。
- **项目场景**：P3 构造 socket/epoll 任何一步失败都关闭已取得 fd；P4 停止线程后 join；P5 `UniqueFd`、`BufferGuard` 和内核 devm 管理不同资源。
- **代码证据**：P3 `src/lslidar_ls_driver/src/input.cc::InputSocket`；P5 `apps/conditiond.cpp`、`kernel/icm20608_iio.c::probe`。证据：`CODE`。
- **工程取舍**：RAII 解决结构性泄漏；Valgrind/ASan、`/proc/<pid>/fd` 和长期监控负责发现遗漏。
- **常见误区**：只盯堆内存，忽略 fd、线程、订阅者和设备 buffer 状态。
- **30 秒回答**：我把泄漏看成所有权问题。LiDAR 的 fd 失败路径显式回收，驱动服务用 RAII，光电线程必须 stop+join；工具检测是第二道防线。
- **2 分钟展开**：描述如何用重复连接/断开测试、fd 数量曲线和 sanitizer 定位增长点。

### A08｜原题 33：字节对齐与 padding

- **一句话结论**：对齐让 CPU 以支持的边界访问对象，编译器可能插入 padding；二进制协议不能直接假设 C 结构布局等于线上的字节布局。
- **从零解释**：不同成员有不同对齐要求，结构大小通常补齐到最大成员对齐的倍数。
- **底层机制**：未对齐访问可能变慢或触发异常；ABI 决定类型布局，但编译选项和架构可能不同。
- **项目场景**：P5 七个 16 位 IIO 通道为 14 字节，时间戳要求 8 字节对齐，因此 scan 中存在 padding，push 前必须清零。
- **代码证据**：P5 `kernel/icm20608_iio.c` 的 scan 结构与 `memset`。证据：`CODE`、`CROSS`。
- **工程取舍**：协议解析使用逐字段或 memcpy，不用 `#pragma pack` 粗暴覆盖所有结构；必要时加 `static_assert(sizeof(...))`。
- **常见误区**：只会算 sizeof，不理解 padding 可能泄露未初始化内核内存。
- **30 秒回答**：IIO scan 的时间戳对齐会产生填充字节，我在驱动 push 前清零整个 scan，不仅保证布局，也避免把内核未初始化数据送到用户态。
- **2 分钟展开**：画出偏移 0～13 的通道、14～15 padding、16～23 时间戳。

## 3. 指针、引用、所有权与 RAII

### A09｜原题 40～43：指针、引用和传参

- **一句话结论**：指针适合表达可空、可改指向和底层地址；引用适合表达必需别名。值传递强调独立副本，const 引用强调只读借用。
- **从零解释**：语法差异背后真正重要的是接口语义，而不是笼统说“引用效率高”。小标量值传递往往最好。
- **底层机制**：实现上引用通常通过地址传递，但语言规则不允许把引用当可空指针随意操作。
- **项目场景**：P5 `Monitor::update(const Sample&)` 表达必需只读输入；`UniqueFd` 用值类型转移所有权；可选输出才使用指针/null。
- **代码证据**：P5 `libcondition` 与 `apps/conditiond.cpp`。证据：`CODE`、`HOST`。
- **工程取舍**：是否使用引用由所有权和可选性决定，不用“底层都是指针”抹平语义。
- **常见误区**：返回局部对象引用、保存超出调用期的借用、把 const 引用误认为深层不可变。
- **30 秒回答**：项目接口用引用表达必需借用，用指针表达可选或底层句柄，用值/移动表达所有权转移。选择首先服务语义，其次才是复制成本。
- **2 分钟展开**：比较 `T`、`const T&`、`T*`、`unique_ptr<T>` 四种接口对调用者的承诺。

### A10｜原题 44、45：野指针与悬空引用

- **一句话结论**：指针指向的对象已经结束生命周期、从未初始化或被错误释放后仍被使用，就会形成悬空/野指针。
- **从零解释**：地址数值可能仍然“看起来正常”，但地址对应对象已经不存在，访问属于未定义行为。
- **底层机制**：释放后的内存可能被重新分配；并发线程继续访问已析构对象会把偶现故障放大。
- **项目场景**：P4 原 detached 线程可能在 QNode 或设备对象析构后继续访问成员，重构为停止标志 + join/wait。
- **代码证据**：P4 `src/mainwindow/src/qnode.cpp`、`rtsp_capture.cpp::stop_thread`。证据：`CODE`。
- **工程取舍**：让拥有者控制线程寿命；裸观察指针不得超过拥有者；容器重分配后不保留旧迭代器。
- **常见误区**：释放后置 null 只能保护一个指针副本，其他别名仍可能悬空。
- **30 秒回答**：光电项目里最危险的不是一个明显的 null，而是 detached 线程持有对象地址。现在析构前先通知停止并 join，再释放资源，从生命周期上消除悬空访问。
- **2 分钟展开**：补充 use-after-free、double free、迭代器失效以及 ASan 的检测方式。

### A11｜原题 46～48：智能指针与 RAII

- **一句话结论**：智能指针只是 RAII 的一种；RAII 是让资源获取与对象生命周期绑定，使所有退出路径自动释放。
- **从零解释**：`unique_ptr` 表示唯一所有权，`shared_ptr` 通过引用计数共享所有权，`weak_ptr` 观察但不延长寿命。
- **底层机制**：析构在作用域退出时确定执行，包括异常展开；shared_ptr 控制块维护强/弱引用计数。
- **项目场景**：P5 用自定义 `UniqueFd` 管 fd、`BufferGuard` 管 IIO enable 状态，说明 RAII 不只管理堆内存；内核用 devm 做 device 生命周期资源管理。
- **代码证据**：P5 `apps/conditiond.cpp::UniqueFd/BufferGuard`、`kernel/icm20608_iio.c::probe`。证据：`CODE`、`HOST`。
- **工程取舍**：能用栈或 unique_ptr 就不用 shared_ptr；共享所有权增加计数、线程同步和环依赖风险。
- **常见误区**：从同一裸指针构造两个 shared_ptr；在析构函数抛异常；把 RAII 等同于“智能指针”。
- **30 秒回答**：项目中 fd 和设备 buffer 都不是内存，但同样用 RAII 管理。`UniqueFd` 不可复制可移动，析构关闭 fd；`BufferGuard` 保证异常退出也关闭 buffer。
- **2 分钟展开**：说明控制块、循环引用、weak_ptr 和自定义 deleter，并对比内核 devm。

## 4. 对象模型与现代 C++

### A12｜原题 54、55、58、59：构造、复制、移动和深浅拷贝

- **一句话结论**：拥有资源的类型必须明确复制和移动语义；默认浅拷贝可能导致两个对象释放同一资源。
- **从零解释**：构造建立不变量，复制产生独立逻辑对象，移动转移资源，析构结束生命周期。
- **底层机制**：编译器可生成特殊成员函数，但一旦类型直接拥有 fd/指针等资源，默认逐成员复制往往错误。
- **项目场景**：P5 `UniqueFd` 删除复制构造/赋值，实现移动并把源 fd 设为 `-1`；因此一个 fd 始终只有一个关闭责任人。
- **代码证据**：P5 `apps/conditiond.cpp:24-42`。证据：`CODE`、`HOST`。
- **工程取舍**：优先 Rule of Zero，让标准容器/智能指针拥有资源；自定义轻量句柄时才实现 Rule of Five。
- **常见误区**：把移动说成一定零成本；移动后对象仍必须可析构但值未指定。
- **30 秒回答**：`UniqueFd` 明确禁止复制、允许移动，移动后源对象置无效，避免二次 close。这是深浅拷贝和 Rule of Five 在真实资源上的落地。
- **2 分钟展开**：说明复制省略、noexcept 对容器移动的影响和自赋值处理。

### B02｜原题 51～67：面向对象、多态与虚函数

五个项目更多使用组合、接口和 RAII，而不是复杂继承。P3 的输入源接口体现运行时多态，P5 则刻意用小型值类型避免继承。需要掌握 vptr/vtable、override、虚析构和对象切片，但不要声称为项目设计重点。

若基类通过基类指针删除派生对象，析构必须为 virtual，否则派生资源可能不释放。构造阶段对象尚未形成完整派生类型，因此构造函数不能 virtual；构造/析构内调用虚函数也不会按普通运行期多态工作。

### A13｜原题 68：容器选择与失效规则

- **一句话结论**：容器选择由访问模式、稳定性、容量上界和内存局部性决定，不是背复杂度表。
- **从零解释**：vector 连续、缓存友好但扩容使指针/迭代器失效；deque 分段；list 节点稳定但局部性差；unordered_map 平均常数查找但有哈希和重哈希成本。
- **底层机制**：底层布局决定分配次数、cache miss 和失效规则。
- **项目场景**：P3 使用 deque/有界队列表达 FIFO 和容量；P5 使用 `std::array` 接收固定数量 epoll 事件和 scan 帧。
- **代码证据**：P3 `core/bounded_queue.h`，P5 `apps/conditiond.cpp`。证据：`CODE`、`HOST`。
- **工程取舍**：实时链路首先设置容量上界；固定大小优先 array；不要为 O(1) 查找盲目引入 unordered_map。
- **常见误区**：只报平均复杂度，不讲最坏情况、迭代器失效与分配行为。
- **30 秒回答**：我在 LiDAR 队列里先确定有界和过载语义，再选择容器；在 epoll 事件数组里数量固定，用 array 避免动态分配。
- **2 分钟展开**：把访问模式、插入位置、稳定性和缓存局部性逐项比较。

### A14｜原题 69：项目里真正使用的 C++11 特性

- **一句话结论**：C++11 的价值不是罗列关键字，而是更准确表达所有权、并发和类型约束。
- **从零解释**：项目最相关的是 move、unique_ptr、atomic、thread、mutex、condition_variable、lambda、chrono、enum class、nullptr、override。
- **底层机制**：这些特性分别把过去靠约定的资源转移、线程同步和类型边界变成编译器可检查的结构。
- **项目场景**：P3 用 mutex/condition_variable 管有界队列；P4 用 atomic 和线程；P5 用移动型 `UniqueFd`、chrono 和 lambda/容器。
- **代码证据**：P3 `core/bounded_queue.h`，P4 `qnode.h`，P5 `conditiond.cpp`。证据：`CODE`、`HOST`。
- **工程取舍**：P5 板端停在 C++14，因为 Linaro GCC 4.9 不完整支持目标 C++17 库；标准选择服从部署工具链。
- **常见误区**：把 C++11 答成关键字清单；认为用了智能指针就没有生命周期问题。
- **30 秒回答**：我主要用 C++11 的 move/RAII、atomic、mutex/condition_variable 和 chrono。它们分别解决资源所有权、跨线程同步和时间表达，不是为“语法新”而使用。
- **2 分钟展开**：逐个关联 P3/P4/P5，并说明为什么没有在板端强推 filesystem。

### A15｜原题 70：左值、右值与移动语义

- **一句话结论**：右值引用允许从即将销毁的对象转移资源；命名后的右值引用变量本身仍是左值。
- **从零解释**：左值通常有可识别身份，右值通常是临时结果。`std::move` 只是类型转换，不执行搬运。
- **底层机制**：移动构造读取源对象资源句柄并把源对象置为可析构状态。
- **项目场景**：P5 `UniqueFd(UniqueFd&&)` 转移 fd；若没有移动语义，就只能传裸 int 或冒险复制关闭责任。
- **代码证据**：P5 `apps/conditiond.cpp::UniqueFd`。证据：`CODE`。
- **工程取舍**：移动类型应尽量 noexcept；不是所有小对象都值得显式移动。
- **常见误区**：return 时到处写 `std::move` 反而阻止返回值优化；使用被移动对象的旧值。
- **30 秒回答**：`std::move` 不移动资源，只把表达式转成可移动类别。真正转移发生在 `UniqueFd` 移动构造里，源 fd 被设为 -1。
- **2 分钟展开**：解释完美转发不是本项目重点，并区分 universal reference 与普通右值引用。

### A16｜原题 71：Lambda 表达式

- **一句话结论**：lambda 是匿名函数对象，关键不是语法短，而是捕获列表决定它持有什么状态和生命周期风险。
- **从零解释**：`[&]` 按引用捕获，`[=]` 按值捕获；显式捕获更容易审查。
- **底层机制**：编译器生成闭包类型，捕获成员成为对象字段；引用捕获不会延长外部对象寿命。
- **项目场景**：异步线程或回调若按引用捕获短生命周期对象，会形成与 detached 线程类似的悬空风险。P4 的修复原则同样适用于 lambda 回调。
- **代码证据**：P4 生命周期修复是风险证据；当前核心代码没有把复杂 lambda 作为主要机制，因此同时标记 `RELATED`。
- **工程取舍**：同步短调用可简化；跨线程回调优先显式捕获稳定所有者或值，不使用宽泛 `[&]`。
- **常见误区**：认为按值捕获后成员对象一定深拷贝；捕获 `this` 只复制指针。
- **30 秒回答**：lambda 的核心是闭包和捕获生命周期。异步场景我避免默认引用捕获，尤其不能让回调保存已经析构对象的 this 指针。
- **2 分钟展开**：补充 mutable、泛型 lambda 和与 `std::function` 类型擦除的开销区别。
