# 五项目结合式嵌入式面试补充讲义

## 这套讲义解决什么问题

这不是另一份孤立的“八股答案合集”，而是《嵌入式八股-赛博二哈》精华版的项目化补充说明。原资料负责给出题目范围，本讲义负责回答四个更难的问题：

1. 这个概念为什么存在，解决了什么工程问题？
2. 它在代码运行过程中到底怎样发生？
3. 五个项目里哪里真正用到了它？
4. 面试时怎样既说清楚，又不把没有做过的事情包装成项目经验？

默认读者已经会写基本 C/C++，使用过 STM32 和 Linux 命令，但对内存模型、并发、I/O 与驱动执行上下文缺少系统联系。首次出现的关键术语会解释；后续章节会直接使用。

## 证据等级

正文只使用以下五种证据标识：

| 标识 | 含义 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| `CODE` | 已存在于仓库 | 设计已经落到源码 | 目标硬件一定正常 |
| `HOST` | 宿主测试通过 | 纯算法、状态机或并发策略满足测试 | 外设时序与实时性 |
| `CROSS` | 目标工具链通过 | 目标架构和指定 API 能编译 | 模块可加载、板端运行稳定 |
| `HIL` | 硬件在环通过 | 指定硬件、版本和实验条件下结果成立 | 所有环境和长期量产可靠性 |
| `TODO-HIL` | 待实板验证 | 边界已明确 | 不得在简历中写成“已验证” |

此外，`RELATED` 表示知识与项目有关，但当前代码并未实现该机制；`BASE` 表示纯基础知识。它们不是较低级的 `CODE`，而是不同性质的内容。

## 原题分级规则

- **A级**：项目中存在真实代码证据。重点题使用“九段式”：原题、结论、从零解释、机制、项目场景、代码证据、设计取舍、追问误区、30 秒/2 分钟回答。
- **B级**：与项目相邻，正文解释如何迁移到项目，但明确说明没有直接实现。
- **C级**：通用算法、Web 或体系结构基础，不强行绑定项目，给出正确回答和学习边界。

完整的 216 题分级和双向索引见 [07-question-mapping.md](07-question-mapping.md)。

阅读不按天数安排，而按依赖关系推进：

```text
语言与资源所有权
        ↓
任务/线程与同步
        ↓
实时边界与过载策略
        ↓
Linux fd 与事件循环
        ↓
设备树 → 驱动 → IIO → 用户服务
        ↓
项目故事、追问树与实验复现
```

每一层达到以下五级才算真正掌握：

1. **能定义**：不用术语循环解释术语。
2. **能画图**：画出对象、线程或数据的流向。
3. **能指代码**：说出仓库、文件和函数。
4. **能跑实验**：知道命令、预期结果和失败表现。
5. **能扛追问**：能说明取舍、反例和验证边界。

## 面试回答模板

### 30 秒版本

```text
定义：它解决什么问题。
场景：我在哪个项目遇到。
实现：具体使用了哪个机制和函数。
取舍：为什么这样选。
边界：什么验证过，什么还没验证。
```

### 2 分钟版本

```text
背景 → 原问题会造成什么后果
机制 → 执行时发生什么
实现 → 数据流、线程/中断边界、关键函数
取舍 → 与替代方案比较
验证 → 测试、交叉编译、HIL 分级
复盘 → 如果继续迭代会怎样做
```

### 不会时的诚实收口

可以说：

> 这个机制我没有在当前项目中直接实现。我的项目使用的是……，二者共同点是……，区别是……。如果要迁移，我会先验证……，所以我不会把它描述成现有项目成果。

不要用模糊的“应该差不多”“底层帮我做了”掩盖边界。准确知道自己没有做过什么，本身就是工程能力。

## 内容维护原则

1. 原资料只作为题目范围，不复制其大段答案。
2. `main` 链接用于日常浏览，`study-step-*` 标签用于固定证据。
3. 新增项目能力时先补测试和证据，再升级题目等级。
4. `HOST/CROSS` 不得改写成 `HIL`。
5. 业务参数、硬件阈值和性能数字没有实验记录就不写确定结论。

## 一次完整的学习闭环

不要以“看完章节”作为结束条件。选一道 A 级题后，先合上文档用自己的语言回答 30 秒；接着在纸上画出数据流、线程或中断边界；然后打开仓库找到对应文件与函数，实际运行相关测试；最后从追问树中随机选三个问题继续回答。任何一步卡住，都回到机制或实验，而不是继续背更长的句子。

建议为每道重点题维护一条简短复盘记录：第一次错误答案、造成错误的概念混淆、代码证据、失败注入结果、当前验证等级。这样能看到自己从“术语记忆”到“工程判断”的变化，也能避免几周后只记得标准答案却忘了为什么。

当代码发生变化时，按下面顺序维护资料：

1. 修改实现并增加能失败的回归测试。
2. 更新项目自己的 `INTERVIEW_EVIDENCE.md`，写清能力和边界。
3. 更新本讲义的项目故事、相关 A 级题与实验。
4. 检查 216 题映射是否仍然唯一、完整。
5. 重新生成 PDF，逐页抽查目录、表格、代码块和链接。
6. 只有获得真实板端记录后，才把 `TODO-HIL` 升级为 `HIL`。

最终目标不是把五个项目说得“无所不能”，而是形成稳定的推理路径：先判断问题属于对象生命周期、并发同步、实时边界、I/O 状态机还是驱动上下文；再选最贴近的项目证据；最后主动说明取舍和验证范围。这样即使面试官换一种问法，也能从机制重新推导，而不是等待命中背过的题目。
