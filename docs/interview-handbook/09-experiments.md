# 实验手册：把回答变成可复现证据

## 1. 为什么面试准备必须包含实验

背诵能回答“是什么”，实验才能回答“你怎么知道”。下面每个实验都固定记录七件事：目的、关联题、前置条件、操作、预期现象、失败注入、面试表达。命令只是入口；真正需要内化的是：改变一个条件后，系统为何呈现对应结果。

证据边界统一使用 `CODE/HOST/CROSS/HIL/TODO-HIL`。宿主机通过不等于实板通过，交叉编译通过也不等于模块能加载。

## 2. P1：融合条件与 Flash CRC 边界

**目的**：验证“多源数据不能仅凭到达就使用”，以及持久化数据为什么同时需要格式校验和 CRC。

- 关联题：12、16、17、20、21、41、81、83。
- 前置条件：进入 P1 仓库，准备可用的 C/C++ 编译器。
- 证据等级：融合门槛和 Flash 损坏注入为 `HOST`，ARMCC 完整构建与 map 边界为 `CROSS`；片内 Flash 擦写与掉电时序仍是 `TODO-HIL`。

操作：按仓库 `README.md` 的 Host Test 命令构建并运行 `fusion_policy` 与 Linux 下的 `flash_store`。后者在测试进程内映射模拟 Flash 页，保存配置后翻转 WiFi 字段的一个字节，再调用实际的 `FlashStore_Load`；另注入擦除失败检查 `FlashStore_Init` 的返回值。

预期现象：不完整样本被融合门槛拒绝；损坏记录被 CRC 拒绝，已有 RAM 配置保持不变；模拟擦除失败时初始化返回失败，而不是假报成功。

失败注入的意义：只测正常路径只能说明函数会返回成功；主动破坏一个字节，才能证明校验真的参与了接受决策。CRC 可以检测常见误码，但不提供抗恶意篡改能力。

Keil 构建实验：用 ARMCC 5.06u6 构建 `Project/MDK-ARM/sud.uvprojx`，检查日志的 0 错误、0 警告和 HEX 生成，再读 `Project/MDK-ARM/Obj/Listings/sud.map` 中的 `LR_IROM1`。当前实测基址 `0x08000000`、占用 `0x90BC`、最大 `0xFC00`，而配置页从 `0x0800FC00` 开始。曾仅修改 IROM 大小但未启用工程的目标内存布局，map 的 Max 仍为无限值；启用后重编才真正形成链接约束。这个实验说明“界面配置了”与“链接器执行了”是两回事。

面试表达：

> 我把“数据有效”拆成来源完整性和持久化完整性。P1 的 Host 测试验证融合门槛，也用映射的模拟 Flash 页翻转一个字节，验证 CRC 拒绝损坏记录且不污染 RAM。这证明了代码逻辑，不证明片内 Flash 擦写和掉电恢复，后者仍是 TODO-HIL。

## 3. P2：非阻塞状态机与 Tick 回绕

**目的**：验证控制流程不会因延时阻塞，并确认无符号差值写法在计数器回绕后仍成立。

- 关联题：30、31、76、77、79、81、84、85、87、88。
- 证据等级：状态机为 `HOST`，ARMCC 完整构建为 `CROSS`；电机、秤和串口联调是 `TODO-HIL`。

正常实验：运行 P2 的状态机测试，让事件按“接单—寻路—到位—称重—完成”进入。检查每步只依据当前状态、事件和时间推进，不在处理函数中长时间等待。

回绕实验：把起始 Tick 放到 `UINT32_MAX` 附近，使截止时间跨过零点。判断使用 `(uint32_t)(now - start) >= timeout`，而不是 `now >= start + timeout`。

预期现象：状态机在到期前保持原状态，到期时只迁移一次；跨零点结果与普通时间段相同。

失败注入：临时把差值判断替换成绝对时间比较，回绕样例应失败。这个失败不是编译错误，而是边界条件下的业务错误。

Keil 构建实验：ARMCC 5.06u6 构建 `Project/MDK-ARM/Fire_FreeRTOS.uvprojx`，当前日志为 0 错误、0 警告并生成 AXF/HEX。检查 `Listing/Fire_FreeRTOS.map`：Flash 使用 `0x4EF8`、上限 `0x10000`；RAM 使用 `0x2808`、上限 `0x5000`。这些约束修正了旧工程里 512 KB / 64 KB 的大芯片遗留设置，防止未来超出 STM32F103C8 容量仍能链接；它们不验证 OLED 启动时序或电机动作。

面试表达：

> 我没有用阻塞延时串联动作，而是让单写者控制任务驱动 FSM。时间判断用无符号差值，因此 Tick 回绕仍可工作；这个结论由边界测试证明，真正的电机动作时长还要实车标定。

## 4. P3：有界队列、过载策略与优雅退出

**目的**：观察生产速度高于消费速度时系统如何退化，以及停止顺序为什么影响死锁和悬空访问。

- 关联题：40、42、53、104、105、109、112、113、119、121、122、127、128。
- 证据等级：`HOST`；真实雷达吞吐是 `TODO-HIL`。

正常实验：按 P3 `README.md` 构建并运行队列测试。记录容量、生产者数量、消费者数量和退出耗时。确认队列未满时 FIFO 顺序成立，关闭后等待线程被唤醒并退出。

过载实验：减慢消费者或连续推送超过容量的数据。观察仓库定义的策略——阻塞、拒绝新数据或丢弃旧数据——并核对计数器，而不是假定“队列会自动解决过载”。

停止实验：先通知停止，再关闭输入源/队列，唤醒条件变量，最后 `join`，然后销毁共享资源。

失败注入：删去关闭时的 `notify_all`，等待线程可能永久睡眠；在 `join` 前销毁队列，可能出现 use-after-free。恢复顺序后测试应稳定结束。

面试表达：

> 有界队列的价值不是让数据不丢，而是让内存上限和过载策略显式化。P3 在关闭时先改变共享状态并唤醒，再 join，最后释放资源。宿主测试验证同步协议；设备吞吐和调度抖动还需要实机压测。

## 5. P4：重连退避、快照与生命周期

**目的**：验证重连不会形成忙循环，读线程不会拿到正在修改的复合对象，析构不会遗留 detached 线程。

- 关联题：17、25、32、39、40、45、47、48、51、52、53、104、105、106、109、112、113、119、126。
- 证据等级：`CODE/HOST/ROS-BUILD`；ROS/Qt 完整编译已通过，ROS 节点与 RTSP 运行联调是 `TODO-HIL`。

退避实验：连续模拟连接失败，记录下一次尝试间隔。预期呈有上限的增长；成功一次后退避状态复位。加入少量抖动可以避免多个客户端同相重连，但当前实现若未使用抖动，不应在面试中说已实现。

快照实验：写线程在 mutex 内更新完整结构，读线程在同一 mutex 下复制后立即解锁，再在锁外处理。预期读者得到同一版本的字段组合，锁的占用时间不包含耗时算法。

生命周期实验：触发停止，检查原子停止标志和 `join` 后释放的顺序。RTSP 的 `VideoCapture::read` 仍可能被底层网络调用阻塞，当前没有证明退出耗时上界；不要声称已实现可靠的阻塞唤醒。

失败注入：把重连间隔固定为零会导致 CPU/日志风暴；返回共享结构的裸引用会把锁外访问暴露给写线程；detach 会让对象析构无法证明线程已经结束。

面试表达：

> 我把 atomic 用于单变量停止状态，mutex 用于需要一致性的复合快照。连接失败采用有上限退避，析构时先停止并 join 再释放采集对象；不过 RTSP 底层读超时尚未完成集成验证，所以我不承诺固定退出时限。

## 6. P5：领域算法、回放与故障状态机

**目的**：在不依赖开发板的情况下验证姿态/冲击判定和传感器失联状态转换。

- 关联题：18、25、46、54、141、142、143、151、189、190。
- 证据等级：`HOST`。

操作：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
./build/apps/conditiond --simulate --samples 200
./build/apps/condition-replay tests/data/normal_then_impact.csv
```

预期现象：单元测试全部通过；模拟服务输出周期样本和状态；回放文件先保持正常，随后进入冲击/异常状态。具体阈值是教学参数，不应包装成产品认证指标。

失败注入：把样本时间戳停止推进，状态机应进入 stale/fault；将单个峰值置于阈值附近，观察防抖或连续样本规则是否避免来回抖动。

面试表达：

> 我先把硬件无关算法抽成 `libcondition`，用合成数据和 CSV 回放验证状态演化；这样驱动没上板时仍能测试业务规则。它不证明真实 IMU 噪声分布，因此阈值最终必须通过板端采集重新标定。

## 7. P5：伪 sysfs 的设备发现与扫描配置

**目的**：证明 sysfs 适配层没有把 `iio:deviceX` 编号写死，并能正确处理缺失属性。

- 关联题：174、175、177、186、188、192、195。
- 证据等级：`HOST`。

操作：运行 `test_iio_sysfs`。测试在临时目录建立最小 IIO 树，写入 `name`、`scan_elements/*_en` 等文件，让适配器按设备名发现目录并配置通道。

预期现象：编号变化不影响发现；名称不匹配、文件缺失、写入失败均返回明确错误；析构或失败路径不遗留打开的 fd。

失败注入：删掉一个必需属性或改写设备名，测试应走失败分支，而不是默默使用错误设备。

面试表达：

> IIO 编号由探测顺序决定，不能写死。我把 sysfs 根目录做成可注入参数，用伪文件树测试按 name 发现和错误路径。这是对用户态适配逻辑的证明，不是对内核驱动 probe 的证明。

## 8. P5：epoll、timerfd、signalfd 与半帧解析

**目的**：理解“事件就绪”不等于“业务消息完整”，以及为何把定时和退出信号纳入同一事件循环。

- 关联题：101、104、105、112、113、119、120、121、122、124、126、127、128、129、130、131、132。
- 证据等级：`CODE/HOST`。

运行 `conditiond --simulate --samples 200`。事件循环同时接收模拟定时器 fd、状态 `timerfd` 和 `signalfd`。定时器驱动状态检查，信号触发有序退出。

半帧实验：运行 `ctest -R scan-assembler --output-on-failure`。测试将 24 字节扫描帧拆成 1+22+余量输入，并一次送入多个帧；只有完整帧才回调，缓存最多保留不足一帧的数据。实际 IIO 字符设备读取仍需上板验证。

失败注入：把 `read` 的返回长度忽略，解析器可能读取旧数据或越界；在 ET 模式下不读到 `EAGAIN`，剩余数据可能没有新的边沿通知。当前代码使用何种触发模式，面试必须以仓库事实为准。

面试表达：

> epoll 只通知 fd 当前可操作，不能提供应用层消息边界。我用有界的残帧缓存按扫描布局拆帧，并限制每轮最多读取 16 次，避免持续输入饿死超时和信号处理；timerfd 和 signalfd 让周期任务与退出进入同一事件循环。

## 9. P5：ARM 用户态交叉编译

**目的**：证明源码和所用标准库接口能被目标工具链接受，并检查产物架构。

- 关联题：69、70、92、93、160、161、162、163。
- 证据等级：`CROSS`。

操作：

```bash
export CROSS_COMPILE=/opt/gcc-linaro/bin/arm-linux-gnueabihf-
cmake -S . -B build-arm \
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/imx6ull-gcc.cmake \
  -DBUILD_TESTING=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build-arm
file build-arm/apps/conditiond
```

预期现象：构建成功；`file` 显示 32 位 ARM EABI5 ELF，动态加载器与板端 rootfs 约定一致。

边界：这不能证明板端动态库版本匹配、设备节点权限正确或运行稳定。部署前还要检查 sysroot、glibc/libstdc++ ABI 和服务用户权限。

## 10. P5：vendor 4.1.15 驱动对象编译

**目的**：用指定内核树验证模块源码与旧版 API 的编译兼容性。

- 关联题：164、165、166、167、169、170、171、172、173、174、175、176、177、178、179、181、182、183、184、185、186、187、188、189、190、191、192、193、194、195、199、202、203。
- 证据等级：`CROSS`，不是 `HIL`。

操作：按 `docs/VALIDATION.md` 指定 vendor Linux 4.1.15 树和交叉工具链构建 `icm20608_iio.o`。检查编译器返回码和目标文件格式。

失败注入：使用主线内核树可能出现 IIO/regmap API 差异；这不应通过随意条件编译掩盖，而应先明确支持矩阵。将 DTS compatible 拼错不会导致 C 编译失败，却会在实板上导致 probe 不发生，这正说明编译验证有边界。

面试表达：

> 驱动对象已在目标 vendor 4.1.15 头文件和 ARM 工具链下通过编译，证明 API 与架构层面的兼容性；我没有把它写成模块加载成功。下一步必须核对 DTB、SPI 波形、WHO_AM_I 和 IIO 缓冲数据。

## 11. fd 泄漏与错误路径观察

**目的**：把 RAII、系统调用错误与 `/proc` 观察联系起来。

- 关联题：18、19、20、21、25、100、101、102、103、132、205、206。
- 证据等级：`HOST`。

步骤：启动模拟服务，记录 `/proc/<pid>/fd` 数量；重复触发可以恢复的打开/关闭路径；比较前后数量。正常情况下，稳定状态的 fd 数不会随循环线性增长。再使用 `strace`（若环境提供）观察 `openat/close/epoll_ctl/read` 返回值。

失败注入：临时在错误返回前跳过 close，fd 数会随重试增加，最终可能遇到 `EMFILE`。恢复 `UniqueFd` 或统一清理路径后，计数应稳定。

不要把“某次计数不变”扩大成“绝无泄漏”；长期压力、第三方库和线程竞争仍需其他工具和场景验证。

## 12. Sanitizer 与并发诊断的适用边界

**目的**：选择与缺陷类型匹配的工具，而不是把所有问题都叫“内存问题”。

| 工具 | 主要发现 | 典型目标 | 不能替代 |
| --- | --- | --- | --- |
| ASan | 越界、use-after-free、部分泄漏 | 解析器和资源生命周期 | 实时性、内核态错误 |
| UBSan | 未定义行为 | 移位、溢出、错误转换 | 数据竞争 |
| TSan | 用户态数据竞争 | P3/P4 线程共享状态 | 目标板时序、驱动锁验证 |
| Valgrind | 泄漏和非法访问，开销较大 | 宿主长期路径 | ARM 实时性能 |
| strace | 系统调用序列与错误码 | fd、网络、文件权限 | 用户态算法正确性 |

诊断顺序：先构造最小可复现输入，再记录版本和参数，使用对应工具定位，最后把复现转成自动测试。工具报告是线索；修复是否正确仍由回归测试和设计不变量决定。

## 13. 实板 HIL 闭环：尚未通过的项目

以下步骤是明确的下一阶段，不得提前改写成 `HIL`：

1. 固化 U-Boot、kernel、DTB、rootfs 和工具链版本。
2. 合入 DTS，启动后从 `dmesg` 确认 compatible 匹配与 probe 日志。
3. 用示波器或逻辑分析仪确认 SPI mode、频率、片选和 WHO_AM_I 事务。
4. 检查 `/sys/bus/iio/devices`、scan elements、scale 和采样频率。
5. 用 `iio_readdev` 或服务读取静止、六面体倾斜和运动数据。
6. 注入拔线、停流、重复冲击、进程重启和服务自启动。
7. 运行至少一次长稳，记录丢样、CPU、内存、温度与错误日志。
8. 保存命令、原始日志、波形和结论，更新 `docs/VALIDATION.md` 后再升级证据等级。

面试遇到“你上板了吗”时，正确回答是说明当前做到哪一级、还差哪一步、怎样验证。清晰边界比虚构“已经跑过”更可信。
